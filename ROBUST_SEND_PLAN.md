# Robust Send Plan

## Goal

Keep request-level `Live LLM calls` close to the saved user-configured limit for the relevant provider when ready work exists and that provider can accept it, without changing provider/model settings. Request admission is local-only: each judge worker uses local request counters as the authority for how many LLM requests it may send for a provider. Cross-worker telemetry is best-effort visibility and bottleneck context, not a distributed lock or an input that lowers local request admission.

## Definitions

- `providerKey`: the canonical request-admission and telemetry bucket. Precedence is saved `providerConnectionId`, then owner-backed synthetic provider connection id from the stored provider invocation context, then `codex:default` for Codex family/default capacity, then `non-codex:default` for all other family/default capacity. The same canonical helper must be used by scheduler, dispatch runtime, request runtime, telemetry, and job-detail UI so no-connection/default buckets are counted the same everywhere and synthetic/default buckets never collapse to `unknown`.
- `providerLimit`: the max-inflight request limit for a provider: the saved user-configured provider limit for saved connection keys, the configured max-inflight for synthetic provider connection keys when present, otherwise the relevant family/default provider capacity for synthetic and default buckets. `providerKey` is only the canonical implementation bucket used to consistently identify that provider across scheduler, runtime, telemetry, and UI. Because there is no distributed lease, each judge worker applies the provider's limit independently against its own local counters for request admission.
- `effectiveProviderLimit`: the current worker-local request-admission target for the same provider after benchmark-preserving runtime gates such as Anthropic warmup and endpoint availability. It is derived from the per-provider `providerLimit` and should not intentionally exceed that provider limit on a worker, but aggregate multi-worker over-cap windows are acceptable.
- `localLiveCalls`: live request count on the current worker for the same `providerKey`. This is the authoritative count for request admission.
- `globalLiveCalls`: best-effort live request count summed across fresh worker telemetry for the same `providerKey`. It is used for display and bottleneck context only, never to reduce the current worker's request-admission target.
- `observedGlobalEffectiveProviderLimit`: best-effort sum of each fresh worker's local `effectiveProviderLimit` for the same `providerKey`. It is an observed aggregate diagnostic value, not an enforceable provider cap, and is never used for request admission.
- `localPromptBacklog`: prompts claimed by the current worker and not yet terminal, including dispatch queued, preparing, waiting for at least one request slot, live request, and persisting states.
- `localRequestWorkBacklog`: active and expected request-attempt work for prompts claimed by the current worker. It includes active request attempts plus a conservative estimate of not-yet-created attempts for prepared/chunked prompts when that estimate is available. Every claimed prompt counts as at least one request-work unit until a more specific estimate is known. The adaptive controller uses this alongside prompt backlog so chunked judging does not hide request pressure behind a small prompt count.
- `localPromptBacklogTarget` and `localRequestWorkBacklogTarget`: worker-local adaptive backlog targets. They are recomputed, not durable authority, and must be exposed in diagnostics next to the matching local backlog values so the UI can explain why claiming increased, held, or stopped.
- `observedGlobalPromptBacklog`: best-effort prompt backlog count summed across fresh worker telemetry for the same `providerKey`. It is used for display and bottleneck context only, not for local request admission.
- `observedGlobalRequestWorkBacklog`: best-effort request-work backlog summed across fresh worker telemetry for the same `providerKey`. It is used for display and bottleneck context only, not for local request admission.
- `endpointProbePermit`: a bounded in-memory permit for endpoint recovery probes, separate from normal request admission. Each worker may hold at most one probe permit per endpoint availability key at a time, probes use existing cooldown/backoff state, and permits are released on success, failure, interruption, worker shutdown, and owner demotion. Probe permits never consume `effectiveProviderLimit` request slots and never increment request-level `Live LLM calls`. A probe permit authorizes only the endpoint health/recovery probe: after a probe succeeds, release the probe permit, mark the endpoint healthy, wake normal request waiters, and reacquire a normal request slot through `withJudgmentRequest` before invoking the judged LLM request. Probe permits must never be reused as request slots. Probes are still physical provider/API calls, so expose local and observed aggregate probe-live diagnostics separately from request fill metrics; no additional physical-call cap is required beyond the bounded probe permit.
- `localEndpointProbeLive`: live endpoint recovery probe count on the current worker for the same endpoint availability key. This is probe diagnostics only, separate from request-level `localLiveCalls`.
- `observedGlobalEndpointProbeLive`: best-effort live endpoint recovery probe count summed across fresh worker telemetry for the same endpoint availability key. This is probe diagnostics only, separate from request-level `globalLiveCalls`.
- `localEndpointProbeState` and `localEndpointProbeCooldownUntil`: current worker's endpoint probe state and cooldown timestamp for the same endpoint availability key. These are local diagnostics; aggregate probe activity is represented by `observedGlobalEndpointProbeLive` and telemetry source metadata.
- No new provider lease table or durable shared request-admission lease state. Cross-worker request admission uses existing worker telemetry/owner-connection discovery and local in-process counters only. Existing SQLite queue rows, owner-completion journal/outbox records, token-use rows, and worker registry snapshots may be extended or reused for lifecycle recovery metadata, including request-attempt ids, but must not be used as distributed leases or remote admission inputs.
- Lifecycle display telemetry is in-memory per worker and/or derived from existing SQLite, journal, token-use, and worker telemetry. Do not add a standalone lifecycle table. Any state needed after worker loss must be recoverable from existing durable records, and unrecoverable in-memory-only stages must reconcile to `telemetryUnavailable` or `workerUnavailable` rather than being reported as precise live attempt state.
- Rollout is fresh-start for active judgment runtime state, but owner-backed handoff evidence is not disposable runtime garbage. During startup, before any scheduler, claim loop, dispatch loop, or request runtime can scan or admit work, run one simple cleanup. For local SQLite-owned jobs, delete or recreate non-terminal local queue rows, non-terminal local journal/outbox runtime rows, runtime manifests, waiter state, and in-memory counters. Any local SQLite-owned active parent job whose runtime state is discarded must be marked `failed` with an error message such as `Judgment runtime state was discarded during robust-send rollout; start the job cleanly to rerun`, so no scheduler can resume against deleted runtime records; a later run recreates runtime state from scratch. For owner-backed judge-worker claims, do not fail the shared parent job as part of worker-local rollout cleanup. Owner-backed accepted claims must be closed on the owner side before local `accepted_claim` state is deleted: first replay or deliver any exact unacked completion/token-use evidence, then send the existing owner claim failure/release/ack path with closeout reason `robustSendRolloutDiscarded` only for claims/attempts that still need rollout closeout, and only delete the local `accepted_claim` after the owner closeout is acknowledged. Do not delete unacked `completion_outbox` rows, `pending_token_use` rows, unimported token-use evidence, or pending owner closeout intents until the owner has acknowledged/imported the exact completion, token-use, or rollout closeout they represent. If the owner is unavailable, keep the minimal existing outbox/journal completion, token-use, or closeout intent needed to retry that owner handoff and keep the claim out of scheduling until the handoff succeeds. Keep terminal historical rows, imported completions, acknowledged owner closeouts, and token-use records. Do not add legacy backfill or compatibility code for pre-plan active rows. After cleanup, every new durable prompt/claim record must have a canonical `providerKey` and initialized request-attempt manifest shape before it can be scheduled. Missing `providerKey`, missing manifest shape, or missing metadata for an actual request attempt is a hard invariant violation rather than a fallback to `unknown`.
- New non-trivial scheduler, controller, request-runtime, telemetry aggregation, and lifecycle recovery flows should use the Effect library (`Effect.gen`, `Layer`, `Context`, `Scope`, and `Schedule` where relevant) so async control flow, resource lifetime, retries, and failures stay explicit.
- Prompt/pipeline concurrency is not the provider limit. The provider limit applies to active LLM requests admitted through `withJudgmentRequest`, including requests produced by chunked judging.
- Prompt lifecycle telemetry and request-attempt lifecycle telemetry are separate. One prompt can create multiple request attempts, especially in chunked judging and retry paths, and each active request attempt must have its own lifecycle record keyed by `jobId`, `providerKey`, prompt queue id, and a request attempt id generated before `waitingForRequestSlot` and preserved through token-use persistence and cleanup.
- Request attempt ids must be written to an existing durable recovery surface before an attempt can block in `waitingForRequestSlot`, so worker-loss reconciliation can close stale attempts one attempt at a time without a new lifecycle table.
- `requestAttemptManifest`: a prompt-owned durable JSON/metadata record on existing rows, not a new lifecycle table. Use local `queue_prompt` for normal SQLite-owned jobs, judge-worker `accepted_claim` for owner-backed claims, and owner import/ack state through `completion_outbox` payload/token-use JSON plus existing `completion_ack`/token-use records. A newly schedulable prompt or claim may have an initialized empty manifest; each actual attempt entry is generated before that attempt can enter `waitingForRequestSlot`. Each attempt entry stores `requestAttemptId`, `providerKey`, state, `createdAt`, `stateStartedAt`, `updatedAt`, optional `baseURL`, optional `tokenUseId`, optional closeout reason, and optional last error. The manifest is for recovery and diagnostics only; it is not a lease and is never a request-admission input. To keep the implementation stable and simple, manifest writes are synchronous only at required state boundaries: before slot wait, when entering live request, when entering persistence, and on closeout. Perform them inside the existing prompt/claim/outbox transaction when one already exists, skip duplicate no-op writes only when all durable fields for the same `requestAttemptId` are unchanged, and do not add a background manifest writer. Same-id same-state updates that add or change `tokenUseId`, closeout reason, persistence subreason, last error, timestamps, or other durable metadata must still write. High-frequency age/duration samples remain in memory and are recomputed from timestamps.
- Manifest retention is bounded. Keep active, waiting, live, persisting, retry-pending, and owner-replay-needed attempts fully detailed. Once a terminal attempt's token-use/outbox/ack closeout is durably recoverable from `token_use.request_attempts_json`, completion outbox, completion ack, or imported token-use records, compact that terminal manifest entry to the minimal recovery/diagnostic shape: `requestAttemptId`, `providerKey`, terminal state, closeout reason, `tokenUseId` or durable closeout reference when present, `createdAt`, and `updatedAt`. Do not compact attempts that can still affect prompt terminal derivation, owner replay/import, retry/requeue decisions, or persistence retry.
- Request-attempt closeout is id-based. Count-only closeout such as `markJudgmentRequestsPersisted(jobId, count)` is not sufficient once one prompt can create multiple request attempts. Closeout must identify exact `requestAttemptId`s so chunked judging, retries, partial token-use persistence, and owner-backed replay can complete, close with a non-success reason, or mark unavailable one attempt at a time.
- Request-attempt terminal state is not the same as prompt terminal state. A `closedRequest` caused by retry, superseded attempt, or prompt requeue closes only that attempt; it must not make the owning prompt `closed` while more retry/requeue work can still be created. Prompt terminal state requires explicit prompt terminal cleanup or recovery closeout confirming no active, pending, retry, or requeue work remains.
- Prompts with zero request attempts are not successful by default. They may become prompt-level `completed` only through an explicit successful no-request terminal reason recorded by terminal cleanup, such as `alreadyJudged` or another named dedupe/no-op success reason in code. Enqueue rejection, skipped dispatch, connection halt, cancellation, prompt recovery, rollout cleanup, article not found, prompt definition not found, missing owner snapshot data, fulltext unavailable, fulltext conversion failure, fulltext too large, and other no-request non-success outcomes must become prompt-level `closed` with a closeout reason, not `completed`.
- `completionPersistence`: persistence after request work finishes, including token-use persistence, local judgment outbox writes, judge-worker completion journal writes, owner ack/import handoff, and local terminal state cleanup. Expose a subreason when one is identifiable.
- Admin/job-detail aggregate telemetry should be `local + fresh remote workers` even when the current process also judges. Expose local and observed aggregate values separately, label aggregate values as best-effort diagnostics rather than enforceable caps, and label remote fetch failures as `telemetryUnavailable` rather than silently presenting local numbers as global numbers.

## SQLite Persistence Boundaries

- Store recovery-critical prompt metadata in existing SQLite/journal surfaces: canonical `providerKey`, prompt queue id, owner claim id, request attempt manifest, persistence closeout state, persistence subreason, last persistence error, and token-use/request-attempt id mapping.
- Store local job-owned recovery data on `queue_prompt`; store judge-worker-owned recovery data on `accepted_claim`; carry owner-backed closeout through `completion_outbox`, `pending_token_use`, `completion_ack`, and imported token-use rows. Add `request_attempts_json` to `app.token_use` and `completion_ack`, and include the same request-attempt array in owner-backed token-use JSON carried by `pending_token_use`, `completion_outbox`, owner completion request bodies, and owner token-use import request bodies. The array stores one entry per physical request attempt with `requestAttemptId`, `providerKey`, prompt queue id, outcome, closeout kind, baseURL when known, prompt/completion/total token counts, started/finished timestamps when known, optional failure code/error, and optional durable closeout reference. Aggregate token-use fields such as `requests`, `successful_requests`, and `failed_requests` remain derived display values only. Owner-backed token-use and completion payloads must preserve one entry per `requestAttemptId`; do not key pending token-use or closeout state only by prompt, claim, article, or count.
- For owner-backed replay/import, exact `requestAttemptId` records are the source of truth. `completion_ack.request_attempts_json` is authoritative completion-handoff closeout evidence for the exact attempt ids it names, imported token-use rows with `app.token_use.request_attempts_json` are authoritative token-use closeout evidence, `completion_outbox` and `pending_token_use` are pending intent, and `accepted_claim` manifests are local recovery evidence. Duplicate attempt ids with identical durable fields are idempotent no-ops, duplicate attempt ids with conflicting provider keys, prompt ownership, outcome, token totals, or closeout kind are hard invariant violations, outbox/pending records without ack/import remain `persisting` or `persistingTokenUse`, and ack/import evidence without a matching pending record still closes only the exact attempt id and closeout kind it names. Never infer closeout from counts when these surfaces disagree.
- Store low-rate ready-work recovery evidence in `job_scan_state` only when the controller or UI must distinguish `noReadyWork` from underfeeding after restart. Do not persist every scheduler sample.
- Keep volatile admission state in memory only: live provider request counters, request-slot waiter queues, worker/fallback slot occupancy, short drain-rate windows, endpoint probe locks/cooldowns, and aggregate remote telemetry snapshots. After worker loss, reconcile missing volatile stages to `telemetryUnavailable` or `workerUnavailable` instead of reporting precise stale state.
- Do not store adaptive backlog targets as authoritative durable state. Recompute targets from SQLite queue truth, local live counters, fresh lifecycle telemetry, endpoint state, and recent in-memory samples.

## Implementation Checklist

- [ ] Add prompt lifecycle states to dispatch telemetry: `claimed`, `dispatchQueued`, `preparing`, `waitingForRequestSlot`, `hasLiveRequest`, `persisting`, `completed`, `closed`, `telemetryUnavailable`, and `workerUnavailable`. Use `closed` with a prompt closeout reason for non-success terminal outcomes such as cancelled, failed, connection halted, prompt recovered, or no-request skipped/rejected. Do not derive prompt `closed` from a retry/requeue `closedRequest` unless prompt terminal cleanup confirms no active, pending, retry, or requeue work remains.
- [ ] Add request-attempt lifecycle states to request telemetry: `waitingForRequestSlot`, `liveRequest`, `persistingTokenUse`, `completedRequest`, `closedRequest`, `telemetryUnavailable`, and `workerUnavailable`. These are separate from prompt states and must support multiple concurrent request attempts per prompt. Use `closedRequest` with a request closeout reason for non-success attempt outcomes rather than reporting failed, cancelled, retried, superseded, or requeued attempts as completed or unavailable. Request closeout reasons must identify whether they are attempt-terminal-only or prompt-terminal candidates.
- [ ] Thread prompt queue id and request attempt id through `withJudgmentRequest`, generated request calls, token-use entries, completion journal/outbox persistence, owner ack/import, and terminal cleanup so request lifecycle records can be closed one attempt at a time.
- [ ] Replace count-only request persistence closeout with id-based closeout. `markJudgmentRequestsPersisted(jobId, count)` should become request-attempt-aware, for example `markJudgmentRequestAttemptsPersisted(jobId, requestAttemptIds)` and `markJudgmentRequestAttemptsClosed(jobId, requestAttemptIds, closeoutReason)`, and tests should cover chunked judging, retries, non-success closeout, and partial persistence failure.
- [ ] Persist request-attempt id ownership and closeout metadata in the prompt-owned request attempt manifest before any attempt waits for a request slot. Newly schedulable prompts/claims need a canonical `providerKey` and initialized empty manifest shape, but do not need request attempt entries until an actual attempt is created. Do not create a standalone lifecycle table. Add `app.token_use.request_attempts_json`, `completion_ack.request_attempts_json`, and the matching owner-backed token-use JSON shape before manifest compaction depends on token-use closeout. Add bounded manifest retention/compaction once terminal attempts are durably recoverable from `request_attempts_json`, outbox, ack, or import records. Add idempotent schema upgrade, token-use request-attempt mapping, and manifest compaction tests for local `queue_prompt`, judge-worker `accepted_claim`, and owner-backed completion/token-use replay surfaces.
- [ ] Store canonical `providerKey` with the durable prompt/claim record at claim time so lifecycle recovery and aggregate telemetry never need to recompute a provider bucket from incomplete runtime context.
- [ ] Make startup/rollout initialize only new-shape judgment runtime state before scheduler startup: delete or recreate non-terminal local SQLite queue/journal runtime records, local manifests, and waiter state; mark only local SQLite-owned active parent jobs whose runtime state was discarded as `failed` with a rollout-discard error message; for owner-backed claims, replay or deliver exact unacked completion/token-use evidence first, close remaining accepted claims on the owner side through the existing owner failure/release/ack path before deleting local `accepted_claim` state, preserve unacked `completion_outbox`, `pending_token_use`, imported token-use, and minimal closeout intents until owner ack/import exists, and do not fail the shared parent job from worker-local cleanup; require `providerKey` and initialized manifest shape on every schedulable prompt/claim; and do not add legacy fallback paths for pre-plan active rows.
- [ ] Record per-state counts and age/duration summaries per `jobId`, `providerKey`, lifecycle kind, and request attempt id where applicable.
- [ ] Define lifecycle ownership: claim code records prompt-level `claimed`, dispatch runtime records prompt-level `dispatchQueued`, prompt preparation records prompt-level `preparing`, request runtime records request-level `waitingForRequestSlot` and `liveRequest`, request lifecycle handoff marks the owning prompt as `waitingForRequestSlot` or `hasLiveRequest` when any active attempt is in those states, persistence records prompt-level `persisting` and request-level `persistingTokenUse`, successful token-use persistence or terminal cleanup records request-level `completedRequest`, request failure/cancellation/retry/supersede/requeue/recovery records request-level `closedRequest` with closeout reason, worker-loss reconciliation records prompt/request `telemetryUnavailable` or `workerUnavailable`, successful terminal cleanup records prompt-level `completed` only after every request attempt for the prompt has reached `completedRequest` and prompt terminal cleanup succeeded, and non-success prompt terminal cleanup records prompt-level `closed` with closeout reason only after confirming no active, pending, retry, or requeue work remains. Attempts marked `telemetryUnavailable` or `workerUnavailable` must not produce prompt-level `completed`.
- [ ] Define derived prompt-state precedence when multiple request attempts exist for one prompt: `hasLiveRequest`, `waitingForRequestSlot`, `persisting`, `workerUnavailable`, `telemetryUnavailable`, `preparing`, `dispatchQueued`, `claimed`, then terminal `completed` only when every attempt is `completedRequest` and prompt terminal cleanup succeeded, or terminal `closed` only when prompt terminal cleanup/recovery explicitly closes the prompt after all attempts are terminal and no active, pending, retry, or requeue work remains. Attempt-terminal-only `closedRequest` records, including retry, superseded attempt, and prompt requeue closeouts, must not make an otherwise active prompt terminal. Keep request-attempt counts visible separately, and make bottleneck classification aggregate request-level persistence independently so a live or waiting attempt cannot hide another attempt stuck in `persistingTokenUse`.
- [ ] Define no-request prompt terminal rules in code, not by vacuous request-attempt checks. Prompts with zero request attempts can become `completed` only when terminal cleanup writes an explicit successful no-request reason such as `alreadyJudged` or another named dedupe/no-op success reason. Enqueue rejection, skipped dispatch, connection halt, cancellation, prompt recovery, rollout cleanup, article not found, prompt definition not found, missing owner snapshot data, fulltext unavailable, fulltext conversion failure, fulltext too large, and other no-request non-success outcomes become `closed` with a reason.
- [ ] Add lifecycle cleanup for enqueue rejection, connection halt, worker shutdown, DuckDB owner demotion, prompt recovery, article not found, prompt definition not found, missing owner snapshot data, fulltext unavailable, fulltext conversion failure, fulltext too large, request failure, and persistence failure.
- [ ] Make request-slot waiter registration interruptible and scoped. Worker, fallback, and Codex waiters must be removed or rejected on prompt recovery, worker shutdown, DuckDB owner demotion, connection halt, and request failure so stale waiters cannot later resolve into zombie work or stale lifecycle records.
- [ ] Add one canonical `providerKey` helper used by add-to-queue ready-target bucketing, scheduler, endpoint availability, connection health, dispatch runtime, request runtime, telemetry, and job-detail UI. It must handle saved `providerConnectionId`, owner-backed synthetic provider connection ids, and family/default buckets consistently.
- [ ] Define a canonical `endpointAvailabilityKey` helper alongside `providerKey`. For saved and owner-backed provider connection buckets, endpoint availability must be keyed by canonical `providerKey` plus a normalized endpoint identity (`effectiveBaseURL` for a base URL, or each manual worker `/v1` URL for worker pools) so one failed endpoint does not gate healthy sibling endpoints under the same provider connection. For Codex and non-Codex default buckets, endpoint availability is shared by provider family/default bucket (`codex:default` or `non-codex:default`) and intentionally must not include `effectiveBaseURL` in the bucket identity. Connection-health rollups may aggregate by `providerKey`, but request gating must use `endpointAvailabilityKey`.
- [ ] Materialize the canonical `providerKey` before add-to-queue and scheduler bucketing and pass it through `RunningJudgmentJob`, capacity buckets, provider/job allocation inputs, claim requests, `PromptToProcess`, `ProviderQueueInput`, `withJudgmentRequest`, endpoint availability keys, worker telemetry input/output, and the job-detail API instead of recomputing it from partially available context in each layer.
- [ ] Make owner-backed running-job and runtime APIs return the canonical `providerKey` and provider limit before claims are made. Do not wait until `getOwnerBackedProviderInvocationContext` inside prompt processing to invent a synthetic provider connection id.

- [ ] Add provider-limit tests for saved provider connections with `maxInflightRequests = null`: they use the relevant family/default capacity, not uncapped capacity and not an implicit limit of `1` unless the family/default capacity is `1`.
- [ ] Keep `withJudgmentRequest` as the only normal LLM request admission point and the only place that updates request-level provider live counters. Endpoint availability probes use a separate scoped endpoint-probe permit and probe telemetry so recovery probes cannot deadlock behind zero effective request capacity. Probe admission is bounded to at most one live probe per endpoint availability key per worker and uses the existing endpoint cooldown/backoff schedule. A successful probe only transitions endpoint state and wakes normal waiters; it must not execute the judged LLM request under the probe permit.
- [ ] Use local in-process live counters keyed by canonical `providerKey` and exposed through existing worker telemetry. - [ ] Use global provider telemetry for display and bottleneck context: sum local plus fresh remote live and backlog counts by `providerKey`, but expose request-specific and backlog-control fields such as `localProviderRequestLimit`, `localProviderLiveRequests`, `localProviderRequestFillPct`, `localPromptBacklog`, `localPromptBacklogTarget`, `localRequestWorkBacklog`, `localRequestWorkBacklogTarget`, `observedGlobalEffectiveProviderLimit`, `observedGlobalProviderLiveRequests`, `observedGlobalProviderRequestFillPct`, `observedGlobalPromptBacklog`, `observedGlobalRequestWorkBacklog`, `localEndpointProbeLive`, `observedGlobalEndpointProbeLive`, `localEndpointProbeState`, and `localEndpointProbeCooldownUntil`. Keep prompt/pipeline slot metrics separate from request metrics, keep endpoint probe diagnostics separate from request fill metrics because probes are physical provider/API calls outside normal request admission, and label observed aggregate limits as best-effort diagnostics rather than enforceable caps.

## Controller Rules

- [ ] Use `effectiveProviderLimit` for local scheduling decisions and display both saved and effective limits when they differ.
- [ ] If `effectiveProviderLimit <= 0`, do not claim more backlog or admit normal LLM requests. Classify the limiter as `endpointUnavailable` with a subreason such as `warmupLimited`, `endpointCooldown`, `endpointMisconfigured`, or `endpointProbe` when known; otherwise use an explicit `effectiveCapacityZero` subreason. Endpoint recovery probes may still run through the separate scoped endpoint-probe permit so cooldown or probing states can recover, but only one probe per endpoint availability key per worker may be live at a time and normal cooldown/backoff must prevent probe storms. When a probe succeeds while normal effective capacity is still zero, only mark the endpoint healthy and report `effectiveCapacityZero`; do not run judged LLM work until normal request admission later has positive capacity and grants a request slot.
- [ ] Compute request-fill thresholds with integer helpers so low provider limits do not underfeed. For positive limits, use `targetLiveCalls = max(1, min(effectiveProviderLimit, ceil(effectiveProviderLimit * 0.95)))` for increase/hold/saturation decisions, while hard request admission still requires `localLiveCalls < effectiveProviderLimit`.
- [ ] If `readyCount > 0` and `localLiveCalls < targetLiveCalls`, increase prompt and request-work backlog targets until live calls rise or a bottleneck is identified.
- [ ] If `localLiveCalls >= targetLiveCalls`, hold the backlog targets and continue replenishing prompt and request-work backlog up to those targets. Reduce only when `localPromptBacklog` or `localRequestWorkBacklog` is above its target and either `localLiveCalls` has stayed at or above `effectiveProviderLimit` for the drain-rate window or completion persistence is backed up.
- [ ] If endpoint availability is `cooldown`, `misconfigured`, or `probing` with no eligible slot, classify `endpointUnavailable` and avoid increasing backlog targets.
- [ ] If `preparing` age grows while `localLiveCalls` is low, classify `promptPreparation`.
- [ ] If `waitingForRequestSlot` grows while `localLiveCalls` is at or above `targetLiveCalls`, classify `providerSaturated`.
- [ ] If `waitingForRequestSlot` grows while `localLiveCalls` is low, endpoint state is healthy, and local worker/fallback slots are available, classify `requestSlotWait`.
- [ ] If `waitingForRequestSlot` grows while `localLiveCalls` is low and worker URLs are locally saturated, classify `workerCapacitySaturated` rather than increasing provider backlog without bound.
- [ ] If `waitingForRequestSlot` grows while `localLiveCalls` is low and shared fallback capacity is saturated, classify `fallbackCapacitySaturated` rather than increasing provider backlog without bound.
- [ ] If `persisting` or `persistingTokenUse` age grows, classify `completionPersistence` and avoid claiming more backlog, even when another request attempt for the same prompt is live or waiting.
- [ ] If aggregate `globalLiveCalls` exceeds `observedGlobalEffectiveProviderLimit`, show aggregate overshoot in diagnostics for all providers but do not lower local request admission from remote telemetry. If only one worker's effective limit is available, label the comparison as aggregate above one observed worker's effective limit for that provider rather than a definitive provider over-cap.
- [ ] If local request telemetry is available but remote telemetry is partial or unavailable, show local scheduling decisions normally and mark aggregate diagnostics as partial.
- [ ] Never change model, provider, thinking level, runtime model, or saved provider limit as part of scheduling.

## Success Criteria

- [ ] With ready work and any positive user-configured provider limit, local request-level `Live LLM calls` on an active judge worker converges toward that configured limit for the provider when the provider can accept it.
- [ ] Aggregate live requests across multiple judge workers are best-effort for all providers and may exceed `observedGlobalEffectiveProviderLimit`; overshoot is visible in diagnostics and should not cause local underfeeding.
- [ ] Local live requests for a provider normally stay at or below that provider's effective limit on each worker; brief local over-limit windows from races are acceptable and should self-correct.
- [ ] If `Live LLM calls` cannot converge, the UI says which stage is limiting throughput.
- [ ] `Claimed` stays bounded by the adaptive prompt backlog target, and chunked judging stays bounded by the adaptive request-work backlog target.
- [ ] Fast GPUs do not drain to zero between scheduler ticks.
- [ ] Endpoint cooldown, misconfiguration, and warmup limits are shown as effective-cap or bottleneck reasons rather than scheduler underfeeding.
- [ ] Provider/model benchmark-critical settings are unchanged.
