# Robust Send Plan

## Goal

Keep request-level `Live LLM calls` close to the saved user-configured limit for the relevant provider when ready work exists and that provider can accept it, without changing provider/model settings. Request admission is local-only: each judge worker uses local request counters as the authority for how many LLM requests it may send for a provider. Cross-worker telemetry is best-effort visibility and bottleneck context, not a distributed lock or an input that lowers local request admission.

## Definitions

- `providerKey`: the canonical request-admission and telemetry bucket. Precedence is saved `providerConnectionId`, then owner-backed synthetic provider connection id from the stored provider invocation context, then `codex:default` for Codex family/default capacity, then `non-codex:default` for all other family/default capacity. The same canonical helper must be used by scheduler, dispatch runtime, request runtime, telemetry, and job-detail UI so no-connection/default buckets are counted the same everywhere and synthetic/default buckets never collapse to `unknown`.
- `providerLimit`: the max-inflight request limit for a provider: the saved user-configured provider limit for saved connection keys, the configured max-inflight for synthetic provider connection keys when present, otherwise the relevant family/default provider capacity for synthetic and default buckets. `providerKey` is only the canonical implementation bucket used to consistently identify that provider across scheduler, runtime, telemetry, and UI. Because there is no distributed lease, each judge worker applies the provider's limit independently against its own local counters for request admission.
- `effectiveProviderLimit`: the current worker-local request-admission target for the same provider after benchmark-preserving runtime gates such as Anthropic warmup and endpoint availability. It is derived from the per-provider `providerLimit` and should not intentionally exceed that provider limit on a worker, but aggregate multi-worker over-cap windows are acceptable.
- `localLiveCalls`: live request count on the current worker for the same `providerKey`. This is the authoritative count for request admission.
- `globalLiveCalls`: best-effort live request count summed across fresh worker telemetry for the same `providerKey`. It is used for display and bottleneck context only, never to reduce the current worker's request-admission target.
- `globalEffectiveProviderLimit`: best-effort sum of each fresh worker's local `effectiveProviderLimit` for the same `providerKey`. It is used for aggregate diagnostics only, never for request admission.
- `localBacklog`: prompts claimed by the current worker and not yet terminal, including dispatch queued, preparing, waiting for at least one request slot, live request, and persisting states.
- `globalBacklog`: best-effort backlog count summed across workers for the same `providerKey`. It is used for display and bottleneck context only, not for local request admission.
- No new provider lease table or durable shared request-admission lease state. Cross-worker request admission uses existing worker telemetry/owner-connection discovery and local in-process counters only. Existing SQLite queue rows, owner-completion journal/outbox records, token-use rows, and worker registry snapshots may be extended or reused for lifecycle recovery metadata, including request-attempt ids, but must not be used as distributed leases or remote admission inputs.
- Lifecycle display telemetry is in-memory per worker and/or derived from existing SQLite, journal, token-use, and worker telemetry. Do not add a standalone lifecycle table. Any state needed after worker loss must be recoverable from existing durable records, and unrecoverable in-memory-only stages must reconcile to `telemetryUnavailable` or `workerUnavailable` rather than being reported as precise live attempt state.
- Rollout is fresh-start for judgment runtime state. Existing local SQLite queue rows, judge-worker journal rows, runtime manifests, active claims, and in-memory counters may be discarded or recreated during rollout. Do not add legacy backfill or compatibility code for pre-plan active rows. After rollout, every new durable prompt/claim/request record must be written in the new shape before it can be scheduled, and missing `providerKey` or request-attempt metadata is a hard invariant violation rather than a fallback to `unknown`.
- New non-trivial scheduler, controller, request-runtime, telemetry aggregation, and lifecycle recovery flows should use the Effect library (`Effect.gen`, `Layer`, `Context`, `Scope`, and `Schedule` where relevant) so async control flow, resource lifetime, retries, and failures stay explicit.
- Prompt/pipeline concurrency is not the provider limit. The provider limit applies to active LLM requests admitted through `withJudgmentRequest`, including requests produced by chunked judging.
- Prompt lifecycle telemetry and request-attempt lifecycle telemetry are separate. One prompt can create multiple request attempts, especially in chunked judging and retry paths, and each active request attempt must have its own lifecycle record keyed by `jobId`, `providerKey`, prompt queue id, and a request attempt id generated before `waitingForRequestSlot` and preserved through token-use persistence and cleanup.
- Request attempt ids must be written to an existing durable recovery surface before an attempt can block in `waitingForRequestSlot`, so worker-loss reconciliation can close stale attempts one attempt at a time without a new lifecycle table.
- `requestAttemptManifest`: a prompt-owned durable JSON/metadata record on existing rows, not a new lifecycle table. Use local `queue_prompt` for normal SQLite-owned jobs, judge-worker `accepted_claim` for owner-backed claims, and owner import/ack state through `completion_outbox` payload/token-use JSON plus existing `completion_ack`/token-use records. Each attempt entry stores `requestAttemptId`, `providerKey`, state, `createdAt`, `stateStartedAt`, `updatedAt`, optional `baseURL`, optional `tokenUseId`, optional closeout reason, and optional last error. The manifest is for recovery and diagnostics only; it is not a lease and is never a request-admission input. To avoid hot-row churn, durable writes are required before slot wait, when entering live request, when entering persistence, and on closeout; high-frequency age/duration samples remain in memory and are recomputed from timestamps.
- Request-attempt closeout is id-based. Count-only closeout such as `markJudgmentRequestsPersisted(jobId, count)` is not sufficient once one prompt can create multiple request attempts. Closeout must identify exact `requestAttemptId`s so chunked judging, retries, partial token-use persistence, and owner-backed replay can complete or mark unavailable one attempt at a time.
- `completionPersistence`: persistence after request work finishes, including token-use persistence, local judgment outbox writes, judge-worker completion journal writes, owner ack/import handoff, and local terminal state cleanup. Expose a subreason when one is identifiable.
- Admin/job-detail aggregate telemetry should be `local + fresh remote workers` even when the current process also judges. Expose local and aggregate values separately, and label remote fetch failures as `telemetryUnavailable` rather than silently presenting local numbers as global numbers.

## SQLite Persistence Boundaries

- Store recovery-critical prompt metadata in existing SQLite/journal surfaces: canonical `providerKey`, prompt queue id, owner claim id, request attempt manifest, persistence closeout state, persistence subreason, last persistence error, and token-use/request-attempt id mapping.
- Store local job-owned recovery data on `queue_prompt`; store judge-worker-owned recovery data on `accepted_claim`; carry owner-backed closeout through `completion_outbox`, `pending_token_use`, `completion_ack`, and imported token-use rows. Owner-backed token-use and completion payloads must preserve one entry per `requestAttemptId`; do not key pending token-use or closeout state only by prompt, claim, article, or count.
- Store low-rate ready-work recovery evidence in `job_scan_state` only when the controller or UI must distinguish `noReadyWork` from underfeeding after restart. Do not persist every scheduler sample.
- Keep volatile admission state in memory only: live provider request counters, request-slot waiter queues, worker/fallback slot occupancy, short drain-rate windows, endpoint probe locks/cooldowns, and aggregate remote telemetry snapshots. After worker loss, reconcile missing volatile stages to `telemetryUnavailable` or `workerUnavailable` instead of reporting precise stale state.
- Do not store adaptive backlog targets as authoritative durable state. Recompute targets from SQLite queue truth, local live counters, fresh lifecycle telemetry, endpoint state, and recent in-memory samples.

## Implementation Checklist

- [ ] Add prompt lifecycle states to dispatch telemetry: `claimed`, `dispatchQueued`, `preparing`, `waitingForRequestSlot`, `hasLiveRequest`, `persisting`, `completed`, `telemetryUnavailable`, and `workerUnavailable`.
- [ ] Add request-attempt lifecycle states to request telemetry: `waitingForRequestSlot`, `liveRequest`, `persistingTokenUse`, `completedRequest`, `telemetryUnavailable`, and `workerUnavailable`. These are separate from prompt states and must support multiple concurrent request attempts per prompt.
- [ ] Thread prompt queue id and request attempt id through `withJudgmentRequest`, generated request calls, token-use entries, completion journal/outbox persistence, owner ack/import, and terminal cleanup so request lifecycle records can be closed one attempt at a time.
- [ ] Replace count-only request persistence closeout with id-based closeout. `markJudgmentRequestsPersisted(jobId, count)` should become request-attempt-aware, for example `markJudgmentRequestAttemptsPersisted(jobId, requestAttemptIds)`, and tests should cover chunked judging, retries, and partial persistence failure.
- [ ] Persist request-attempt id ownership and closeout metadata in the prompt-owned request attempt manifest before any attempt waits for a request slot. Do not create a standalone lifecycle table. Add idempotent schema upgrade tests for local `queue_prompt`, judge-worker `accepted_claim`, and owner-backed completion/token-use replay surfaces.
- [ ] Store canonical `providerKey` with the durable prompt/claim record at claim time so lifecycle recovery and aggregate telemetry never need to recompute a provider bucket from incomplete runtime context.
- [ ] Make startup/rollout initialize only new-shape judgment runtime state: clear or recreate active local queue/journal runtime records as needed, require `providerKey` and request-attempt metadata on every schedulable prompt/claim, and do not add legacy fallback paths for pre-plan active rows.
- [ ] Record per-state counts and age/duration summaries per `jobId`, `providerKey`, lifecycle kind, and request attempt id where applicable.
- [ ] Define lifecycle ownership: claim code records prompt-level `claimed`, dispatch runtime records prompt-level `dispatchQueued`, prompt preparation records prompt-level `preparing`, request runtime records request-level `waitingForRequestSlot` and `liveRequest`, request lifecycle handoff marks the owning prompt as `waitingForRequestSlot` or `hasLiveRequest` when any active attempt is in those states, persistence records prompt-level `persisting` and request-level `persistingTokenUse`, token-use persistence or terminal cleanup records request-level `completedRequest`, worker-loss reconciliation records prompt/request `telemetryUnavailable` or `workerUnavailable`, and terminal cleanup records prompt-level `completed` only after all request attempts for the prompt have completed or been marked unavailable.
- [ ] Define derived prompt-state precedence when multiple request attempts exist for one prompt: `hasLiveRequest`, `waitingForRequestSlot`, `persisting`, `workerUnavailable`, `telemetryUnavailable`, `preparing`, `dispatchQueued`, `claimed`, then `completed` only when all attempts and prompt terminal cleanup are closed. Keep request-attempt counts visible separately so prompt precedence does not hide request-level bottlenecks.
- [ ] Add lifecycle cleanup for enqueue rejection, connection halt, worker shutdown, DuckDB owner demotion, prompt recovery, request failure, and persistence failure.
- [ ] Make request-slot waiter registration interruptible and scoped. Worker, fallback, and Codex waiters must be removed or rejected on prompt recovery, worker shutdown, DuckDB owner demotion, connection halt, and request failure so stale waiters cannot later resolve into zombie work or stale lifecycle records.
- [ ] Add one canonical `providerKey` helper used by add-to-queue ready-target bucketing, scheduler, endpoint availability, connection health, dispatch runtime, request runtime, telemetry, and job-detail UI. It must handle saved `providerConnectionId`, owner-backed synthetic provider connection ids, and family/default buckets consistently.
- [ ] Keep endpoint availability keyed by provider family/default bucket only for default capacity. For saved or owner-backed provider connection buckets, endpoint availability uses the same canonical `providerKey`; for Codex and non-Codex default buckets, endpoint availability is shared by provider family and must not include `effectiveBaseURL` in the bucket identity.
- [ ] Materialize the canonical `providerKey` before add-to-queue and scheduler bucketing and pass it through `RunningJudgmentJob`, capacity buckets, provider/job allocation inputs, claim requests, `PromptToProcess`, `ProviderQueueInput`, `withJudgmentRequest`, endpoint availability keys, worker telemetry input/output, and the job-detail API instead of recomputing it from partially available context in each layer.
- [ ] Make owner-backed running-job and runtime APIs return the canonical `providerKey` and provider limit before claims are made. Do not wait until `getOwnerBackedProviderInvocationContext` inside prompt processing to invent a synthetic provider connection id.
- [ ] Add provider-key tests for canonical precedence: saved connections, owner-backed synthetic connection ids when `providerConnectionId` is missing, Codex default buckets, non-Codex default buckets, endpoint availability/connection health keys, add-to-queue ready-target buckets, and missing `providerConnectionId` that should not become `unknown`.
- [ ] Add provider-limit tests for saved provider connections with `maxInflightRequests = null`: they use the relevant family/default capacity, not uncapped capacity and not an implicit limit of `1` unless the family/default capacity is `1`.
- [ ] Keep `withJudgmentRequest` as the only request admission point and the only place that updates request-level provider live counters.
- [ ] Use local in-process live counters keyed by canonical `providerKey` and exposed through existing worker telemetry. Increment before the LLM request or probe starts, release in `finally`, and allow aggregate over-limit windows when workers race or operate independently.
- [ ] Make local provider live counters authoritative for sending requests. Do not subtract remote `globalLiveCalls` or `globalBacklog` from the local request target.
- [ ] Use global provider telemetry for display and bottleneck context: sum local plus fresh remote live and backlog counts by `providerKey`, but expose request-specific fields such as `localProviderRequestLimit`, `localProviderLiveRequests`, `globalProviderRequestLimit`, `globalProviderLiveRequests`, and `providerRequestFillPct`. Keep prompt/pipeline slot metrics separate from request metrics.
- [ ] Ignore stale worker telemetry using the existing owner-connection freshness/staleness signal for display and bottleneck classification so dead workers do not confuse the UI.
- [ ] Treat missing or slow remote telemetry as `telemetryUnavailable` for diagnostics, not as a reason to reduce local request admission.
- [ ] Return telemetry source metadata from the job detail API: local worker id, fresh remote worker count, stale worker count, unavailable worker count, and whether aggregate values are complete or partial.
- [ ] Keep a bounded claim batch size after the adaptive controller is in place. Remove fixed `16/64` behavior only after replacing it with a dynamic batch capped by a safe max transaction size.
- [ ] Add a provider/job backlog target computed from `effectiveProviderLimit`, `localLiveCalls`, `localBacklog`, active prompts, queued prompts, ready count, recent drain rate, endpoint availability, and current lifecycle ages. Use global telemetry only as diagnostic context.
- [ ] Define the adaptive controller constants in code with tests: safe minimum backlog, safe maximum backlog, drain-rate window, stage-age thresholds, and hysteresis bands for increasing/decreasing backlog.
- [ ] Implement the adaptive controller, request-slot waiter cancellation, and lifecycle recovery logic with Effect so retries, backoff, scoped cleanup, interruption, and failure reporting are explicit and testable.
- [ ] Add an owner-backed ready-work signal or claim-result-based fallback so the adaptive controller can distinguish `noReadyWork` from underfed request admission when workers claim through the owner API.
- [ ] Claim more prompts when `localLiveCalls` is below the controller increase threshold, ready work exists, endpoint state permits dispatch, and local backlog is below target.
- [ ] Stop increasing backlog when local backlog is above target, endpoint state blocks dispatch, or completion persistence is backed up.
- [ ] When local provider request slots appear saturated, keep topping up backlog to the target so fast GPUs do not drain between scheduler ticks, but do not grow backlog beyond the target.
- [ ] Make prompt preparation concurrency dynamic instead of fixed at `16`.
- [ ] Bound preparation concurrency with a safe minimum/maximum so DB/CPU work cannot explode.
- [ ] Track prompts waiting for request slots separately from prompts doing preparation.
- [ ] Keep prompt/pipeline concurrency high enough to avoid underfeeding `withJudgmentRequest`, but never use prompt concurrency as the request cap.
- [ ] Add request-level accounting for chunked judging so one prompt that produces multiple LLM requests still consumes a provider request slot for each active request and reports each request attempt separately in telemetry.
- [ ] Define persistence-failure semantics: token-use persistence, judgment outbox, completion journal, owner ack, and terminal cleanup failures keep the affected prompt/request in `persisting` or `persistingTokenUse` with subreason and last error until the normal persistence retry loop succeeds, owner outbox replay/import acks it, prompt recovery requeues it, or worker-loss reconciliation marks it `telemetryUnavailable` or `workerUnavailable`. Existing catch-and-continue token-use persistence paths must become lifecycle-aware: do not close request attempt ids, mark request attempts `completedRequest`, or mark the owning prompt `completed` until the relevant persistence has actually succeeded or one of the explicit recovery closeout events has occurred. Only those closeout events may transition failed persistence records to `completed`, `completedRequest`, `telemetryUnavailable`, or `workerUnavailable`.
- [ ] Change token-use persistence, pending token-use journaling, completion outbox payloads, completion ack payloads, and imported token-use rows to carry exact `requestAttemptId`s. Chunked judging and retries must persist and close multiple attempts for the same prompt independently, including partial success/failure cases.
- [ ] Classify bottlenecks as `claiming`, `promptPreparation`, `requestSlotWait`, `providerSaturated`, `workerCapacitySaturated`, `fallbackCapacitySaturated`, `completionPersistence`, `endpointUnavailable`, or `noReadyWork`.
- [ ] Expose the bottleneck classification from the job detail API, including optional subreasons for `completionPersistence` such as `tokenUsePersistence`, `judgmentOutbox`, `completionJournal`, `ownerAck`, and `terminalCleanup`, and optional request-slot subreasons such as `workerCapacity`, `fallbackCapacity`, `providerLimit`, `endpointProbe`, and `waiterInterrupted`.
- [ ] Update `/admin/jobs/:id` to show the bottleneck state next to queue/request metrics.
- [ ] Make `Claimed`, `Running Prompts`, `Worker active prompts`, `Worker queued prompts`, and `Live LLM calls` use consistent lifecycle definitions based on `providerKey` and claim/request lifecycle state. Rename or split existing `providerActive*` UI/API fields so request-level metrics cannot be confused with prompt/pipeline slot metrics, and update route contracts, UI types, and route/UI tests in the same change.
- [ ] Reconcile lifecycle telemetry after worker crash or telemetry loss: preserve SQLite/journal-derived queue truth, mark missing in-memory stages as `telemetryUnavailable` or `workerUnavailable`, and avoid classifying stale in-memory ages as real bottlenecks.
- [ ] Add tests for underfed provider, saturated provider, slow claim path, slow prep path, request-slot wait path, endpoint cooldown/misconfiguration, Anthropic warmup/effective cap behavior, multi-worker aggregate overshoot diagnostics, owner-backed judge-worker handoff, and lifecycle cleanup.

## Controller Rules

- [ ] Use `effectiveProviderLimit` for local scheduling decisions and display both saved and effective limits when they differ.
- [ ] If `readyCount > 0` and `localLiveCalls < effectiveProviderLimit * 0.95`, increase target backlog until live calls rise or a bottleneck is identified.
- [ ] If `localLiveCalls >= effectiveProviderLimit * 0.95`, hold the backlog target and continue replenishing backlog up to that target. Reduce only when `localBacklog` is above target and either `localLiveCalls` has stayed at or above `effectiveProviderLimit` for the drain-rate window or completion persistence is backed up.
- [ ] If endpoint availability is `cooldown`, `misconfigured`, or `probing` with no eligible slot, classify `endpointUnavailable` and avoid increasing backlog.
- [ ] If `preparing` age grows while `localLiveCalls` is low, classify `promptPreparation`.
- [ ] If `waitingForRequestSlot` grows while `localLiveCalls` is near the effective limit, classify `providerSaturated`.
- [ ] If `waitingForRequestSlot` grows while `localLiveCalls` is low, endpoint state is healthy, and local worker/fallback slots are available, classify `requestSlotWait`.
- [ ] If `waitingForRequestSlot` grows while `localLiveCalls` is low and worker URLs are locally saturated, classify `workerCapacitySaturated` rather than increasing provider backlog without bound.
- [ ] If `waitingForRequestSlot` grows while `localLiveCalls` is low and shared fallback capacity is saturated, classify `fallbackCapacitySaturated` rather than increasing provider backlog without bound.
- [ ] If `persisting` or `persistingTokenUse` age grows, classify `completionPersistence` and avoid claiming more backlog.
- [ ] If aggregate `globalLiveCalls` exceeds `globalEffectiveProviderLimit`, show aggregate overshoot in diagnostics but do not lower local request admission from remote telemetry. If only one worker's effective limit is available, label the comparison as aggregate above one observed worker's effective limit for that provider rather than a definitive provider over-cap.
- [ ] If local request telemetry is available but remote telemetry is partial or unavailable, show local scheduling decisions normally and mark aggregate diagnostics as partial.
- [ ] Never change model, provider, thinking level, runtime model, or saved provider limit as part of scheduling.

## Success Criteria

- [ ] With ready work and any positive user-configured provider limit, local request-level `Live LLM calls` on an active judge worker converges toward that configured limit for the provider when the provider can accept it.
- [ ] Aggregate live requests across multiple judge workers are best-effort and may exceed the summed effective provider limits observed in fresh telemetry; overshoot is visible in diagnostics and should not cause local underfeeding.
- [ ] Local live requests for a provider normally stay at or below that provider's effective limit on each worker; brief local over-limit windows from races are acceptable and should self-correct.
- [ ] If `Live LLM calls` cannot converge, the UI says which stage is limiting throughput.
- [ ] `Claimed` stays bounded by the adaptive backlog target.
- [ ] Fast GPUs do not drain to zero between scheduler ticks.
- [ ] Endpoint cooldown, misconfiguration, and warmup limits are shown as effective-cap or bottleneck reasons rather than scheduler underfeeding.
- [ ] Provider/model benchmark-critical settings are unchanged.
