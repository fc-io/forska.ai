# Robust Send Plan

## Goal

Keep provider-wide request-level `Live LLM calls` close to, and normally at or below, the saved user-configured max-inflight limit for the relevant provider when ready work exists and that provider can accept it, without changing provider/model settings. `maxInflightRequests` is a provider-bucket limit: not per worker, not per model, and not shared globally across unrelated providers. Normal request admission must acquire a provider-scoped shared request lease for the canonical `providerKey`; local counters are diagnostics and leak detection, not the source of admission authority. Cross-worker telemetry is best-effort visibility and bottleneck context, not a substitute for the shared lease check.

## Definitions

- `providerKey`: the canonical request-admission and telemetry bucket. Precedence is saved `providerConnectionId`, then owner-backed synthetic provider connection id from the owner-supplied provider bucket snapshot returned before claim, then `codex:default` for Codex family/default capacity, then a provider-scoped non-Codex default key such as `${provider}:default` for the relevant provider's default capacity. Owner-backed synthetic provider connection ids must be deterministic and stable for the same owner provider bucket across owner restarts, workers, and claims; derive them from owner-owned bucket identity/fingerprint data, not random per-claim or per-run ids. Non-Codex default buckets are shared across models for the same provider, but must not be shared globally across unrelated providers. The same canonical helper must be used by scheduler, dispatch runtime, request runtime, telemetry, and job-detail UI so no-connection/default buckets are counted the same everywhere and synthetic/default buckets never collapse to `unknown`.
- `workerProcess`: one running server or judge-worker process that can claim prompts and invoke LLM requests. Multiple worker processes may serve the same provider bucket, but they share the same provider-wide request limit through the shared lease authority.
- `providerLimit`: the provider-wide max-inflight provider/API call limit for a `providerKey`: for saved connection keys, use the saved `maxInflightRequests` when non-null and otherwise the relevant provider/default capacity; for owner-backed synthetic provider connection keys, use `maxInflightRequests` only from the owner-supplied provider bucket snapshot returned before claim, and otherwise the relevant provider/default capacity; for Codex default buckets, use Codex default capacity; for non-Codex default buckets, use the relevant provider's default capacity. The owner/server admission service is authoritative for the current provider limit for each `providerKey`; workers pass `providerKey` plus the `providerLimitVersion` from their owner-supplied bucket snapshot, but acquire must validate that version against owner-side current bucket state and return `staleProviderLimitSnapshot` without creating a new lease when the worker's snapshot is stale. Non-owner workers and prompt-local request runtime must not fetch live provider settings or infer limits from model settings during request admission. Normal LLM requests use request leases, endpoint probes use probe leases, and the sum of both lease kinds must stay within this provider-wide limit. The limit is shared by all worker processes for the same provider bucket, shared across models for that provider bucket, and never shared globally across unrelated providers.
- `providerLimitVersion`: owner-generated monotonic version, updated-at token, or bucket revision attached to each provider bucket snapshot. It changes whenever saved `maxInflightRequests`, provider default capacity, synthetic/default bucket identity, or other admission-critical bucket inputs change. All acquire calls include it; same-holder idempotent reacquire may return an existing lease without changing occupancy, but any acquire that would insert a new lease rejects stale versions before count/insert. Diagnostics surface the current version/limit so schedulers refresh instead of over-admitting after a limit decrease.
- `effectiveProviderLimit`: the current worker-local routeable live normal-request ceiling for the same provider after benchmark-preserving runtime gates such as Anthropic warmup, worker/fallback capacity, and routeable endpoint availability. It is a ceiling before subtracting current `localProviderLiveRequests`, bounded by `providerLimit`, and excludes transient shared lease occupancy, so provider saturation does not look like endpoint or warmup unavailability. Local routeable request headroom is `max(0, effectiveProviderLimit - localProviderLiveRequests)`; worker/fallback occupancy must feed the ceiling and not be subtracted a second time unless a separate capacity system is not represented in `localProviderLiveRequests`. Normal request admission requires both positive local routeability and a successful provider-wide lease acquire. Endpoint availability only lowers this worker's effective ceiling when no routeable endpoint remains for that provider bucket on the current worker; a single failed endpoint in a multi-endpoint pool must not zero the provider while other endpoint availability keys are healthy.
- `localProviderLiveRequests`: live normal request count on the current worker for the same `providerKey`. This is diagnostic and must match the worker's held live request leases after reconciliation, but it is not authoritative for provider-wide request admission.
- `providerLeasedLiveRequests`: authoritative live normal request lease count for the same `providerKey` across all worker processes, derived from shared lease state and cross-checked with fresh worker telemetry. It includes suspect fresh-holder request leases until the owner reconciliation path deletes the live row and records any diagnostic quarantine outside `app.provider_admission_lease`. It is used to decide whether to attempt request admission, for display, and for bottleneck context, but no request is admitted without a successful atomic lease acquire; stale or unavailable telemetry must not change the shared lease count.
- `providerLeasedProbeCalls`: authoritative live endpoint probe lease count for the same `providerKey` across all worker processes. Probe leases share the provider-wide physical-call cap with normal request leases but remain separate from request-level `Live LLM calls`.
- `providerAvailableRequestLeases`: derived provider-wide normal request admission headroom using the current owner-side provider bucket snapshot: `max(0, providerLimit - providerLeasedLiveRequests - providerLeasedProbeCalls)`, before local routeability gates. This is a scheduling hint; hard admission still requires an atomic lease acquire with a non-stale `providerLimitVersion`.
- `providerRequestFillPct`: provider-wide request fill percentage derived as `providerLeasedLiveRequests / normalRequestCapacity`, where `normalRequestCapacity = max(0, providerLimit - providerLeasedProbeCalls)`. When `normalRequestCapacity` is zero, report fill as unavailable/`null` and show probe occupancy separately rather than fabricating a percentage.
- `localProviderRequestFillPct`: worker-local request fill percentage derived as `localProviderLiveRequests / effectiveProviderLimit`. When `effectiveProviderLimit` is zero, report fill as unavailable/`null`; do not subtract provider-wide shared lease occupancy or probe leases from this denominator because endpoint probe occupancy is shown separately.
- `observedGlobalProviderLiveRequests`: best-effort sum of each fresh worker's `localProviderLiveRequests` for the same `providerKey`. It excludes endpoint probes and is diagnostic only; lease rows remain the authoritative admission count.
- `observedGlobalProviderRequestFillPct`: best-effort observed request fill percentage derived as `observedGlobalProviderLiveRequests / observedGlobalEffectiveProviderLimit` using only fresh workers that report both values. When no fresh denominator exists, report fill as unavailable/`null`; when telemetry is partial, compute from the fresh subset and mark the aggregate as partial in telemetry source metadata.
- `observedGlobalEffectiveProviderLimit`: best-effort sum of each fresh worker's local routeable `effectiveProviderLimit` for the same `providerKey`. It is an observed aggregate diagnostic value, not an enforceable cap. The enforceable cap is the provider-wide `providerLimit`.
- `providerRequestLease`: a shared provider-scoped admission record for one live normal request attempt, keyed by `providerKey`, globally unique `requestAttemptId`, and holder worker id with an expiry/heartbeat timestamp. `requestAttemptId` must be generated as a globally unique UUID/ULID-like id before manifest write and may still be displayed with `jobId` and prompt queue id for diagnostics. Creating a new lease must validate the current owner fencing token and `providerLimitVersion`, then atomically check the owner-side held request plus probe lease count against the current owner-side `providerLimit`; same-holder idempotent reacquire returns the existing row without new admission. The lease and `localProviderLiveRequests` mirror are released through the current owner admission service when the physical LLM call ends, before the attempt enters `persistingCompletion`; persistence can continue without occupying provider request capacity. Holder-token release is also used for interruption and worker shutdown only while current owner fencing accepts the operation. If the admission owner is demoted before release, the demoted process must not mutate shared lease state; the new/current owner releases the row only through an accepted holder-token request, stale/demoted-holder reconciliation, or exact durable request-attempt closeout. Leases are request-admission authority only, not prompt lifecycle truth, not model-specific capacity, and not a globally shared pool across providers.
- `providerProbeLease`: a shared provider-scoped admission record for one live endpoint recovery probe, keyed by `providerKey`, `endpointAvailabilityKey`, globally unique `probeAttemptId`, and holder worker id with an expiry/heartbeat timestamp. Creating a new probe lease must validate the current owner fencing token and `providerLimitVersion`, then atomically check the owner-side held request plus probe lease count against the current owner-side `providerLimit`; same-holder idempotent reacquire returns the existing row without new admission. Probe lease release uses the same current-owner fencing, exact holder-token release, and stale/missing/demoted/suspect reconciliation mechanics as request leases, but never request-attempt terminal closeout; probe closeout requires holder release, stale/missing/demoted holder reconciliation, or suspect-fresh proof for the exact probe lease identity.
- `localPromptBacklog`: prompts claimed by the current worker and not yet terminal, including dispatch queued, preparing, waiting for at least one request slot, live request, and persisting states.
- `localRequestWorkBacklog`: active and expected request-attempt work for prompts claimed by the current worker. It includes active request attempts plus a conservative estimate of not-yet-created attempts for prepared/chunked prompts when that estimate is available. Every claimed prompt counts as at least one request-work unit until a more specific estimate is known. The adaptive controller uses this alongside prompt backlog so chunked judging does not hide request pressure behind a small prompt count.
- `localPromptBacklogTarget` and `localRequestWorkBacklogTarget`: worker-local adaptive backlog targets. They are recomputed, not durable authority, and must be exposed in diagnostics next to the matching local backlog values so the UI can explain why claiming increased, held, or stopped.
- `observedGlobalPromptBacklog`: best-effort prompt backlog count summed across fresh worker telemetry for the same `providerKey`. It is used for display and bottleneck context only, not for shared provider request admission.
- `observedGlobalRequestWorkBacklog`: best-effort request-work backlog summed across fresh worker telemetry for the same `providerKey`. It is used for display and bottleneck context only, not for shared provider request admission.
- `endpointProbePermit`: a bounded in-memory permit plus shared provider-scoped probe lease for endpoint recovery probes, separate from normal request admission but still within the provider-wide physical-call cap. Each worker may hold at most one probe permit per endpoint availability key at a time, probes use existing cooldown/backoff state, and local permits are dropped on success, failure, interruption, worker shutdown, and owner demotion. Shared probe leases are deleted only through the current owner admission service by exact holder-token release or current-owner reconciliation; a demoted admission owner must not delete them directly. Probe permits never consume normal request slots and never increment request-level `Live LLM calls`, but normal request leases plus probe leases for the same `providerKey` must not exceed `providerLimit`. A probe permit authorizes only the endpoint health/recovery probe: after a probe succeeds, release the probe permit and probe lease, mark the endpoint healthy, wake normal request waiters, and reacquire a normal request slot through `withJudgmentRequest` before invoking the judged LLM request. Probe permits must never be reused as request slots. Probes are still physical provider/API calls, so expose local and observed aggregate probe-live diagnostics separately from request fill metrics.
- `localEndpointProbeLive`: live endpoint recovery probe count on the current worker for the same endpoint availability key. This is probe diagnostics only, separate from request-level `localProviderLiveRequests`.
- `observedGlobalEndpointProbeLive`: best-effort live endpoint recovery probe count summed across fresh worker telemetry for the same endpoint availability key. This is probe diagnostics only, separate from request-level `providerLeasedLiveRequests`.
- `localEndpointProbeState` and `localEndpointProbeCooldownUntil`: current worker's endpoint probe state and cooldown timestamp for the same endpoint availability key. These are local diagnostics keyed by `endpointAvailabilityKey`; aggregate probe activity is represented by `observedGlobalEndpointProbeLive` and telemetry source metadata. When a provider/job can route to multiple endpoints, expose endpoint diagnostics as a per-endpoint list plus provider-level summary rather than collapsing mixed endpoint states into one ambiguous status.
- Provider-wide request admission uses the owner/server DuckDB app database as the shared authority, not local SQLite. Add a focused live-only `app.provider_admission_lease` table through the DuckDB migration flow and acquire/release/heartbeat leases only through the owner/server admission service. Release and expiry delete rows from this live table when the provider/API call is no longer live; closeout and recovery evidence belongs only in existing manifest/outbox/token-use surfaces, and closed lease history must not be retained in `app.provider_admission_lease`. The table columns are `provider_key TEXT NOT NULL`, `lease_kind TEXT NOT NULL` (`request` or `probe`), `lease_identity_key TEXT NOT NULL`, nullable `request_attempt_id` for request leases, nullable `endpoint_availability_key` and `probe_attempt_id` for probe leases, `holder_worker_id TEXT NOT NULL`, `holder_run_id TEXT NOT NULL`, `acquired_at_ms BIGINT NOT NULL`, `last_heartbeat_at_ms BIGINT NOT NULL`, and `expires_at_ms BIGINT NOT NULL`. Build `lease_identity_key` as `request:${requestAttemptId}` for request leases and `probe:${endpointAvailabilityKey}:${probeAttemptId}` for probe leases so DuckDB nullable unique behavior cannot weaken lease identity enforcement. Add `CHECK (lease_kind IN ('request', 'probe'))`, `CHECK (acquired_at_ms <= last_heartbeat_at_ms)`, `CHECK (last_heartbeat_at_ms < expires_at_ms)`, and one shape check requiring request rows to have non-null `request_attempt_id` plus null endpoint/probe ids, and probe rows to have null `request_attempt_id` plus non-null endpoint/probe ids. Enforce uniqueness with `UNIQUE(provider_key, lease_kind, lease_identity_key)`, and index `(provider_key, expires_at_ms)`. Existing SQLite queue rows, owner-completion journal/outbox records, token-use rows, and worker registry snapshots may be extended or reused for lifecycle recovery metadata, including request-attempt ids, but lifecycle records must not be treated as request-admission leases.
- The owner/server admission service must be the only writer for `app.provider_admission_lease`, and workers must never perform direct local DB writes for admission. For a given DuckDB app database, only the current DuckDB owner process may run the admission service; non-owner processes and judge workers must call/proxy to that owner. Every acquire, heartbeat, release, and expiry operation must include or verify the current DuckDB owner fencing token/run epoch before mutating lease rows, and a demoted/stale owner must fail closed without admitting or deleting leases. The service must serialize all acquire, heartbeat, release, and expiry operations per `providerKey` before touching the table and hold the per-provider serialization until the DuckDB transaction commits or rolls back; the DuckDB transaction still performs expiry/count/insert atomically, but per-provider serialization is mandatory so count-then-insert cannot over-admit under concurrent worker calls or multiple incoming worker requests.
- Acquire is idempotent by lease identity. After owner-fencing validation succeeds, if a request lease already exists for `(provider_key, lease_kind, lease_identity_key)` with the same `holder_worker_id` and `holder_run_id`, return the existing lease as acquired before provider-limit-version rejection, without incrementing occupancy or changing `acquired_at_ms`; heartbeat may extend `last_heartbeat_at_ms` and `expires_at_ms`, including when the same holder reacquires an expired-but-suspect lease that has not been released by reconciliation. If the same identity exists for a different fresh holder, return `alreadyHeld` and do not admit. If the same identity exists for a stale holder, validate the current `providerLimitVersion` before expiring that row; after expiry, retry acquire in the same serialized admission operation. Probe leases follow the same rules keyed by `probe:${endpointAvailabilityKey}:${probeAttemptId}`.
- Holder release and heartbeat must be compare-and-delete/update operations scoped by the full holder token: `provider_key`, `lease_kind`, `lease_identity_key`, `holder_worker_id`, and `holder_run_id`. A release or heartbeat with a non-matching holder token is an idempotent `notHolder` no-op; it must never delete, extend, or close another run's lease. Worker shutdown may request holder release through the current owner only for leases owned by that exact holder token. Owner demotion never authorizes the demoted process to mutate rows; the current owner may run a separate `expireStaleLease` path that deletes stale, missing, demoted, or durably terminal holder rows only after the grace/suspect rules below are satisfied.
- Define provider lease timing constants in code with tests: `leaseHeartbeatIntervalMs`, `leaseTtlMs`, `leaseStaleWorkerGraceMs`, and `leaseSuspectFreshWorkerMaxMs`. The owner/server admission service sets lease timestamps with one owner clock using integer epoch milliseconds UTC and must be wired through an injectable clock, holder-freshness lookup, owner-fencing lookup, current provider-limit snapshot lookup, and serialized admission store/layer so tests can use a fake clock and controllable worker registry.
- Non-idempotent acquire runs one serialized owner/server operation that validates owner fencing, validates the caller's `providerLimitVersion` against current owner-side bucket state, reconciles only stale rows allowed by the holder grace/suspect rules, counts every remaining non-deleted request plus probe lease for `providerKey` including expired-but-suspect fresh-holder rows, and inserts only when the held count is below the current owner-side `providerLimit`. Same-holder idempotent reacquire is handled by the acquire-order rule below before provider-limit-version rejection and is not new admission.
- For expiry, a missing holder registry entry is stale only after `max(expiresAtMs, acquiredAtMs + leaseStaleWorkerGraceMs) < nowMs` unless durable terminal closeout exists for the exact request attempt. Explicit owner demotion may mark the holder stale immediately for reconciliation, but holder release still must be scoped by holder token and current owner fencing. Long-running LLM calls must keep heartbeating until the physical call finishes. If a lease is past `expiresAtMs` but the holder is still fresh, report it as suspect and continue counting it as held; if the fresh holder no longer reports the exact held lease identity/requestAttemptId/probeAttemptId after `leaseSuspectFreshWorkerMaxMs`, `expireStaleLease` may delete the live lease row and record suspect-lease diagnostic/quarantine evidence outside `app.provider_admission_lease`, otherwise keep it suspect but held.
- If `providerLimit` is lowered below currently held leases, existing physical calls and probes are allowed to finish, no new request or probe leases are admitted until total held request plus probe leases fall below the new limit, and diagnostics show provider over-limit drain-down without mutating model/provider settings.
- Provider lease acquire order is authoritative and testable: validate owner fencing first; read the exact lease identity; return an existing same-holder lease without new admission, occupancy changes, holder identity changes, or `acquired_at_ms` changes; return `alreadyHeld` for a different fresh holder; validate current `providerLimitVersion` for every non-idempotent path; expire a stale same-identity holder only after that version validation; reconcile other stale/missing/demoted rows allowed by grace/suspect rules; count every remaining non-deleted request plus probe lease including suspect fresh-holder rows; insert only when the held count is below the current owner-side `providerLimit`.
- Provider-admission lease quarantine is diagnostic-only and never a retained live lease state. When reconciliation proves a suspect fresh-holder lease releasable but needs an audit/repair marker, delete the live row from `app.provider_admission_lease` in the same fenced current-owner operation and record quarantine evidence on existing diagnostic or repair surfaces outside that live table. Diagnostic/quarantined lease evidence must not count as held capacity, and retained live rows must never be described as quarantined.
- Lifecycle display telemetry is in-memory per worker and/or derived from existing SQLite, journal, token-use, and worker telemetry. Do not add a standalone lifecycle table. Any state needed after worker loss must be recoverable from existing durable records, and unrecoverable in-memory-only stages must reconcile to `telemetryUnavailable` or `workerUnavailable` rather than being reported as precise live attempt state.
- Use `workerUnavailable` only when the holder worker heartbeat/registry entry is stale, missing, or explicitly demoted. Use `telemetryUnavailable` when the holder worker is still fresh but lifecycle telemetry cannot be fetched, decoded, or matched to the durable attempt. Do not use either state for known request failures, cancellations, retries, superseded attempts, or prompt requeues; those must use explicit `closedRequest` reasons.
- Rollout is fresh-start for active judgment runtime state, but completion and owner-backed handoff evidence is not disposable runtime garbage. During startup, before any scheduler, claim loop, dispatch loop, or request runtime can scan or admit work, run durable phases in order: preserve/import local and owner-backed completion or token-use evidence, record owner-backed closeout intents and close owner claims, delete or recreate discarded active runtime rows, then assign local job state. A later phase cannot advance until the prior phase is durably observable on existing job, claim, outbox, ack, token-use, or closeout-intent records.
- Local SQLite-owned rollout cleanup starts by flushing/importing or preserving unexported `judgment_outbox` rows and any token-use/request-attempt evidence that names completed or persisting attempts. Preserved local evidence makes the parent job importable but non-schedulable; local `judgment_outbox` rows with `exported_at IS NULL` are durable completion evidence, not runtime rows to delete. Delete or recreate non-terminal local queue runtime records, local manifests, and waiter state only after completion evidence is imported, resolved, or preserved in an importable state.
- Local rollout job states are exclusive. Use `storage_state = 'draining'` while any unexported local outbox row, unimported token-use evidence, legacy-pending evidence, or local evidence quarantine remains. Use `failedImportable` only if that named state is implemented and every import/repair query explicitly includes it. Use plain `failed` with the rollout-discard message only after no unexported, unimported, legacy-pending, or quarantined local completion evidence remains. Plain `failed` must never be the state that keeps preserved evidence importable.
- Rollout importability must explicitly handle pre-plan durable completion evidence that lacks `request_attempts_json` or exact `requestAttemptId`s. Before any new exact-attempt invariant checker runs on preserved rows, startup must choose one named, restart-safe path per legacy evidence row: convert/import it with a deterministic `legacyRequestAttemptId` derived from the durable row identity and a `legacyRolloutImported` closeout marker when ownership, provider, outcome, and token fields are sufficient for idempotent comparison; keep it `draining` with `legacyCompletionEvidencePendingRepair` when safe import is not provable yet; or quarantine it with `legacyCompletionEvidenceQuarantined` while keeping import/repair queries in scope. Quarantined legacy evidence remains pending for local state assignment unless `failedImportable` exists and includes that quarantine in import scope. This is a one-time evidence preservation/repair path, not a legacy scheduling fallback for discarded runtime rows.
- For owner-backed judge-worker claims, do not fail the shared parent job as part of worker-local rollout cleanup. Owner-backed rollout closeout intent must be durable before any owner call: record the exact claim ids, request attempt ids, closeout reason `robustSendRolloutDiscarded`, and retry state on an existing accepted-claim/journal/outbox surface, replay or deliver exact unacked completion/token-use evidence first, then send the existing owner claim failure/release/ack path only for claims/attempts that still need rollout closeout. Delete local `accepted_claim` state only after owner closeout ack or equivalent durable import evidence exists.
- Do not delete unacked `completion_outbox` rows, `pending_token_use` rows, unimported token-use evidence, local unexported `judgment_outbox` rows, or pending owner closeout intents until the owner/local importer has acknowledged or imported the exact completion, token-use, or rollout closeout they represent. If the owner or local importer is unavailable, keep the minimal existing outbox/journal completion, token-use, or closeout intent needed to retry that handoff and keep the claim/prompt out of scheduling until the handoff succeeds. Keep terminal historical rows, imported completions, acknowledged owner closeouts, and token-use records.
- Rollout cleanup must be restart-safe and idempotent at every phase. If a worker crashes between local outbox import/preservation, owner closeout ack, local runtime row deletion, and local parent-job state assignment, the next startup must rerun cleanup without double-importing completions, losing unacked owner-backed evidence, deleting still-needed closeout intent, or making preserved local outbox rows non-importable.
- Do not add legacy backfill or compatibility code for pre-plan active rows. After cleanup, every new durable prompt/claim record must have a canonical `providerKey` and initialized request-attempt manifest shape before it can be scheduled. Missing `providerKey`, missing manifest shape, or missing metadata for an actual request attempt is a hard invariant violation rather than a fallback to `unknown`.
- Provider-admission lease cleanup must also be restart-safe. On startup and worker-loss detection, expire or release only leases whose holder is stale, missing after grace, or demoted by the holder rules; request leases whose exact `requestAttemptId` has durable terminal closeout; or expired-but-suspect fresh-holder leases past `leaseSuspectFreshWorkerMaxMs` whose holder no longer reports the exact held lease identity/requestAttemptId/probeAttemptId. For suspect-fresh cleanup, delete the live lease row and quarantine only diagnostic evidence outside `app.provider_admission_lease`. Do not delete live leases for another healthy worker, and do not let stale unreconciled leases permanently underfeed the provider.
- Durable terminal `requestAttemptId` closeout releases request leases only. Probe leases do not have request-attempt closeout evidence and may be released only through holder-token release, stale/missing/demoted holder reconciliation, or the suspect-fresh proof path for the exact probe lease identity.
- Use the Effect library (`Effect.gen`, `Layer`, `Context`, `Scope`, and `Schedule` where relevant) for new non-trivial scheduler, controller, request-runtime, telemetry aggregation, and lifecycle recovery flows so async control flow, resource lifetime, retries, and failures stay explicit.
- Prompt/pipeline concurrency is not the provider limit. The normal request portion of the provider limit applies to active LLM requests admitted through `withJudgmentRequest`, including requests produced by chunked judging; endpoint probes use separate probe leases but still count against the same provider-wide physical-call cap.
- Prompt lifecycle telemetry and request-attempt lifecycle telemetry are separate. One prompt can create multiple request attempts, especially in chunked judging and retry paths, and each active request attempt must have its own lifecycle record keyed by `jobId`, `providerKey`, prompt queue id, and a request attempt id generated before `waitingForRequestSlot` and preserved through token-use persistence and cleanup.
- Request attempt ids must be written to an existing durable recovery surface before an attempt can block in `waitingForRequestSlot`, so worker-loss reconciliation can reconcile stale or unavailable attempts one attempt at a time without a new lifecycle table.
- `requestAttemptManifest`: a prompt-owned durable JSON/metadata record on existing rows, not a new lifecycle table. Use local `queue_prompt` for normal SQLite-owned jobs, judge-worker `accepted_claim` for owner-backed claims, and owner import/ack state through `completion_outbox` payload/token-use JSON plus existing `completion_ack`/token-use records. A newly schedulable prompt or claim may have an initialized empty manifest; each actual attempt entry is generated before that attempt can enter `waitingForRequestSlot`. Each attempt entry stores `requestAttemptId`, `providerKey`, state, `createdAt`, `stateStartedAt`, `updatedAt`, optional `baseURL`, optional `tokenUseId`, optional closeout reason, and optional last error. The manifest is for recovery and diagnostics only; it is not a lease and is never a request-admission input. To keep the implementation stable and simple, manifest writes are synchronous only at required state boundaries: before slot wait, when entering live request, when entering persistence, and on closeout. Perform them inside the existing prompt/claim/outbox transaction when one already exists, skip duplicate no-op writes only when all durable fields for the same `requestAttemptId` are unchanged, and do not add a background manifest writer. Every manifest write must transactionally merge the current persisted manifest by `requestAttemptId`; never replace the whole manifest from a stale in-memory snapshot. Concurrent writes for sibling attempts, especially chunked judging attempts for the same prompt, must preserve unrelated entries and reload/retry ordinary compare-and-swap or update conflicts; fail loudly only when a reloaded manifest reveals an invariant conflict or bounded retry exhaustion. Same-id same-state updates that add or change `tokenUseId`, closeout reason, persistence subreason, last error, timestamps, or other durable metadata must still write. High-frequency age/duration samples remain in memory and are recomputed from timestamps.
- Add `request_attempt_manifest_json JSON NOT NULL DEFAULT '[]'` and `request_attempt_manifest_version INTEGER NOT NULL DEFAULT 0` to every manifest-owning surface that lacks them, including local `queue_prompt` and judge-worker `accepted_claim`. Manifest updates must use compare-and-swap: reload current JSON/version, merge by `requestAttemptId`, then `UPDATE ... SET request_attempt_manifest_json = ?, request_attempt_manifest_version = request_attempt_manifest_version + 1 WHERE id = ? AND request_attempt_manifest_version = ?`. If zero rows are updated, reload and retry.
- Define `manifestCasMaxAttempts`, `manifestCasRetryBaseDelayMs`, and jitter in code with tests. CAS exhaustion before an attempt enters `waitingForRequestSlot` must keep the owning prompt/claim non-schedulable in prompt-level `persisting` with subreason `manifestCasExhausted` and `lastPersistenceError`, without acquiring a provider lease. That prompt/claim must be picked up by the same persistence repair loop and deadline semantics as other prompt-level persistence failures; before the deadline, retry the manifest write with backoff, and after the deadline report `requiresRepair` while keeping the job/provider blocked from new claiming rather than silently completing or closing the prompt. CAS exhaustion while writing request closeout/completion metadata must keep the request in `persistingCompletion` with subreason `manifestCasExhausted` and `lastPersistenceError`. In both cases, do not drop sibling attempt entries, silently close attempts, invent a new lifecycle state, or mark the prompt completed.
- Request-attempt manifest state transitions must be monotonic per `requestAttemptId`. The normal success path is `waitingForRequestSlot` to `liveRequest` to `persistingCompletion` to `completedRequest`. `completedRequest` and `closedRequest` are terminal sinks except for idempotent same-state metadata enrichment. `telemetryUnavailable` and `workerUnavailable` are recovery diagnostic states, not final closeout if later authoritative token-use, outbox, ack, import, or closeout evidence arrives for the exact `requestAttemptId`; that evidence may supersede the unavailable state through a forward recovery transition. Stale writes must not move an attempt backward, erase `tokenUseId`, closeout reason, persistence subreason, durable closeout reference, or last error, or overwrite newer timestamps. Out-of-order async writes must reload, merge, and either become idempotent no-ops, valid same-state metadata updates, valid forward transitions, valid durable-evidence supersession of an unavailable diagnostic state, or hard invariant errors.
- Unavailable diagnostic states must not become permanent limbo. Recovery must periodically repair exact `telemetryUnavailable` and `workerUnavailable` attempts: if later durable evidence exists, supersede the diagnostic state with that evidence; if no evidence appears by the repair deadline, either requeue the owning prompt with a new request attempt or convert the attempt to `closedRequest` with an explicit recovery closeout reason such as `workerLostNoDurableResult`, then let prompt terminal cleanup decide prompt-level completion or closure.
- Define `requestAttemptRepairDeadlineMs` in code with tests. The repair deadline starts at `stateStartedAt` for `telemetryUnavailable` or `workerUnavailable`; local SQLite-owned prompts may requeue with a new attempt id when inputs are still valid, while owner-backed claims must use the owner closeout/release path before local deletion. Before creating a replacement attempt id, atomically transition the old exact attempt to `closedRequest(workerLostRequeued)` or `closedRequest(telemetryUnavailableRequeued)` so prompt terminal logic never sees two active versions of the same lost attempt. After the deadline, an unavailable diagnostic must either be superseded by exact durable evidence, requeued with a new attempt id after closing the old attempt, or converted to `closedRequest` with an explicit recovery reason.
- Exact durable evidence that arrives after an unavailable diagnostic has already been converted to `closedRequest(workerLostNoDurableResult)` must not silently rewrite the prompt result. Preserve it on the relevant existing evidence surface (`judgment_outbox`, `completion_outbox`, or `pending_token_use`) with a `quarantinedLateEvidence` status/closeout marker, surface an invariant diagnostic, and require explicit repair/import handling; normal import/token-use closeout must reject that attempt until repair resolves the quarantine.
- Manifest retention is bounded. Keep active, waiting, live, persisting, retry-pending, and owner-replay-needed attempts fully detailed. Once a terminal attempt's token-use/outbox/ack closeout is durably recoverable from `token_use.request_attempts_json`, local `judgment_outbox.request_attempts_json`, completion outbox, completion ack, or imported token-use records, compact that terminal manifest entry to the minimal recovery/diagnostic shape: `requestAttemptId`, `providerKey`, terminal state, closeout reason, `tokenUseId` or durable closeout reference when present, `createdAt`, and `updatedAt`. Compacted terminal attempts remain visible only in request-attempt diagnostics and aggregate attempt counts; prompt-level success summaries use prompt terminal state and must not treat earlier retry, superseded, or requeued `closedRequest` attempts as prompt failure after a later success. Do not compact attempts that can still affect prompt terminal derivation, owner replay/import, retry/requeue decisions, or persistence retry.
- Request-attempt closeout is id-based. Count-only closeout such as `markJudgmentRequestsPersisted(jobId, count)` is not sufficient once one prompt can create multiple request attempts. Closeout must identify exact `requestAttemptId`s so chunked judging, retries, partial token-use persistence, and owner-backed replay can complete, close with a non-success reason, or mark an attempt diagnostically unavailable one attempt at a time while still allowing later exact durable evidence to supersede that diagnostic state.
- Request-attempt terminal state is not the same as prompt terminal state. A `closedRequest` caused by retry, superseded attempt, or prompt requeue closes only that attempt; it must not make the owning prompt `closed` while more retry/requeue work can still be created, and it must not block a later prompt-level `completed` when a successful attempt or explicit no-request success reason exists. Prompt terminal state requires explicit prompt terminal cleanup or recovery closeout confirming no active, pending, retry, or requeue work remains.
- Prompts with zero request attempts are not successful by default. They may become prompt-level `completed` only through an explicit successful no-request terminal reason recorded by terminal cleanup, such as `alreadyJudged` or another named dedupe/no-op success reason in code. Enqueue rejection, skipped dispatch, connection halt, cancellation, prompt recovery, rollout cleanup, article not found, prompt definition not found, missing owner snapshot data, fulltext unavailable, fulltext conversion failure, fulltext too large, and other no-request non-success outcomes must become prompt-level `closed` with a closeout reason, not `completed`.
- `completionPersistence`: persistence after request work finishes, including token-use persistence, local judgment outbox writes, judge-worker completion journal writes, owner ack/import handoff, and prompt terminal cleanup. The request-attempt lifecycle state for request-attempt closeout persistence is `persistingCompletion`; subreasons such as `tokenUsePersistence`, `judgmentOutbox`, `completionJournal`, and `ownerAck` identify the blocked request-attempt surface. Prompt terminal cleanup is a prompt-level `persisting` subreason and is not a prerequisite for request-attempt `completedRequest`. A request attempt must not enter `completedRequest` until every required request-attempt closeout surface for that attempt is durable or explicitly closed by a recovery event.
- Required completion surfaces by path: local SQLite-owned successful request requires token-use persistence when tokens exist and local `judgment_outbox.request_attempts_json`; owner-backed successful request requires judge-worker completion journal/outbox intent, owner completion ack/import evidence, and owner-backed token-use import when tokens exist; retry/requeue/supersede closeout requires an exact `closedRequest` manifest entry plus any owner release/ack required for owner-backed claims; no-request success or closure requires no fabricated request attempt. `completedRequest` means the relevant request-attempt surfaces for that path are durable. Prompt terminal cleanup is a separate later step that derives prompt `completed` or `closed` after all attempts are terminal and must not be a prerequisite for `completedRequest`.
- Define persistence retry constants in code with tests: `completionPersistenceRetryBaseDelayMs`, `completionPersistenceRetryMaxDelayMs`, and `completionPersistenceRepairDeadlineMs`. Before the repair deadline, keep retrying with backoff and expose `completionPersistence` plus subreason/last error. After the deadline, keep the job/provider blocked from new claiming, mark diagnostics as `requiresRepair`, and either continue safe idempotent replay or use an explicit repair action; do not silently mark the request or prompt complete and do not discard durable completion evidence.
- Admin/job-detail aggregate telemetry should show provider lease-authoritative counts plus observed `local + fresh remote workers` telemetry even when the current process also judges. Expose local, provider lease, and observed aggregate values separately; label observed aggregate values as best-effort diagnostics rather than enforceable caps, and label remote fetch failures as `telemetryUnavailable` rather than silently presenting local numbers as global numbers.

## SQLite Persistence Boundaries

- Store recovery-critical prompt metadata in existing SQLite/journal surfaces: canonical `providerKey`, prompt queue id, owner claim id, request attempt manifest, persistence closeout state, persistence subreason, last persistence error, and token-use/request-attempt id mapping.
- Naming boundaries are explicit: TypeScript, Eden/API route JSON, telemetry fields, request-attempt manifests, and `request_attempts_json` payload entries use camelCase names such as `providerKey`, `requestAttemptId`, `baseURL`, `createdAt`, and `tokenUseId`; SQL tables, columns, indexes, and constraints use snake_case names such as `provider_key`, `request_attempt_id`, `lease_identity_key`, `created_at_ms`, and `token_use_id`. Mapper code must translate at database/API boundaries, route contracts must not expose SQL-only names, and SQL migrations must not use camelCase JSON field names as physical column names unless an existing JSON payload already stores them.
- Store local job-owned recovery data on `queue_prompt`; store judge-worker-owned recovery data on `accepted_claim`; carry local completion closeout through `judgment_outbox`; carry owner-backed closeout through `completion_outbox`, `pending_token_use`, `completion_ack`, and imported token-use rows. Add `request_attempts_json` JSON columns with `NOT NULL DEFAULT '[]'` to `app.token_use`, local SQLite `judgment_outbox`, and local SQLite `completion_ack`; add matching owner-backed token-use JSON in `pending_token_use`, `completion_outbox`, owner completion request bodies, and owner token-use import request bodies. The array stores one entry per physical request attempt with `requestAttemptId`, `providerKey`, prompt queue id, outcome, closeout kind, baseURL when known, prompt/completion/total token counts, started/finished timestamps when known, optional failure code/error, and optional durable closeout reference. Request-attempt JSON timestamps must use integer epoch milliseconds UTC as the canonical format; if an existing surface serializes another format, normalize both sides before conflict comparison and write the canonical format for new records. Aggregate token-use fields such as `requests`, `successful_requests`, and `failed_requests` remain derived display values only. Owner-backed token-use and completion payloads must preserve one entry per `requestAttemptId`; do not key pending token-use or closeout state only by prompt, claim, article, or count. For local job SQLite, use `queue_prompt_id`; for judge-worker journal surfaces, use `queue_record_id`. Add `queue_record_id` and `request_attempt_id` to `pending_token_use`, and make its request-attempt-aware identity at least `(job_id, queue_record_id, request_attempt_id)` plus any existing owner/claim routing columns needed for delivery. Merge-validated arrays are allowed for payload comparison and import idempotency only, never as the primary pending-token-use identity.
- For owner-backed replay/import, exact `requestAttemptId` records are the source of truth. `completion_ack.request_attempts_json` is authoritative completion-handoff closeout evidence for the exact attempt ids it names, imported token-use rows with `app.token_use.request_attempts_json` are authoritative token-use closeout evidence, `completion_outbox` and `pending_token_use` are pending intent, and `accepted_claim` manifests are local recovery evidence. Duplicate attempt ids with identical durable fields are idempotent no-ops, duplicate attempt ids with conflicting provider keys, prompt ownership, outcome, token totals, or closeout kind are hard invariant violations, outbox/pending records without ack/import remain `persisting` or `persistingCompletion`, and ack/import evidence without a matching pending record still closes only the exact attempt id and closeout kind it names, including superseding prior `telemetryUnavailable` or `workerUnavailable` diagnostics for that exact attempt. Never infer closeout from counts when these surfaces disagree.
- Cross-surface closeout conflicts are hard invariant errors. If the same `requestAttemptId` appears in token-use, local outbox, completion outbox, completion ack, pending token-use, or imported token-use surfaces with different provider keys, prompt ownership, outcome, closeout kind, or durable closeout references, do not pick a winner by precedence; only exact duplicate data and unavailable-diagnostic supersession by later authoritative durable evidence are allowed. Optional fields such as token totals, baseURL, and timestamps are conflicts only when the surface is required to know that field or when two surfaces both provide the field and the normalized values disagree; absence of an optional field on a closeout-only surface is not a conflict by itself.
- Token-use idempotency must verify conflicts, not only suppress duplicate inserts. On token-use id conflict, reload the existing row and compare `request_attempts_json` plus all durable token-use fields; identical data is a no-op, and any mismatch in attempt ids, provider keys, prompt ownership, token totals, outcome, closeout kind, normalized timestamps when present, or durable closeout references is a hard invariant error. Formatting-only timestamp differences are not durable conflicts after normalization. Do not treat `ON CONFLICT DO NOTHING` as successful idempotency without this verification.
- Existing durable rows created before `request_attempts_json` are not compared by the new exact-attempt conflict rules until they have passed through the named legacy import/repair/quarantine path. Conversion must preserve the original durable row id/reference in the generated attempt entry so repeated startup cleanup can prove idempotency and late conflicts can be traced back to the pre-plan evidence.
- Store low-rate ready-work recovery evidence in `job_scan_state` only when the controller or UI must distinguish `noReadyWork` from underfeeding after restart. Do not persist every scheduler sample.
- Keep local admission mirror state in memory only: live provider request counters, request-slot waiter queues, worker/fallback slot occupancy, short drain-rate windows, endpoint probe locks/cooldowns, and aggregate remote telemetry snapshots. Shared provider request/probe leases are the only admission state that may be durable/shared. After worker loss, expire or reconcile stale provider leases before reporting capacity, and reconcile missing volatile lifecycle stages to `telemetryUnavailable` or `workerUnavailable` instead of reporting precise stale state.
- Do not store adaptive backlog targets as authoritative durable state. Recompute targets from SQLite queue truth, shared provider lease availability, the `localProviderLiveRequests` mirror, fresh lifecycle telemetry, endpoint state, and recent in-memory samples.

## Controller Rules

- [ ] Use `providerLimit`, provider-wide shared lease availability, and `effectiveProviderLimit` for scheduling decisions, and display saved provider limit, provider-wide leased live requests, available request leases, and local effective routeable capacity when they differ.
- [ ] Apply bottleneck classification in a stable precedence order when multiple conditions are true: `completionPersistence`, `endpointUnavailable`, `effectiveCapacityLimited`, `workerCapacitySaturated`, `fallbackCapacitySaturated`, `providerSaturated`, `providerAtTarget`, `promptPreparation`, `requestSlotWait`, `claiming`, then `noReadyWork`.
- [ ] If `effectiveProviderLimit <= 0`, do not claim more backlog or admit normal LLM requests on that worker. Classify no healthy/eligible endpoint availability key as `endpointUnavailable` with subreasons such as `endpointCooldown`, `endpointMisconfigured`, or `endpointProbe`; classify non-endpoint gates such as Anthropic warmup or local routeable capacity zero as `effectiveCapacityLimited` with subreasons such as `warmupLimited` or `effectiveCapacityZero`. Endpoint recovery probes may still run through the separate scoped endpoint-probe permit and shared probe lease so cooldown or probing states can recover, but only one probe per endpoint availability key per worker may be live at a time, normal cooldown/backoff must prevent probe storms, and request leases plus probe leases must remain within `providerLimit`. When a probe succeeds while normal effective capacity is still zero, only mark the endpoint healthy and report the remaining effective-capacity limiter; do not run judged LLM work until normal request admission later has positive local routeable capacity and grants a provider request lease.
- [ ] Compute request-fill thresholds with integer helpers so low provider limits do not underfeed. First compute `normalRequestCapacity = max(0, providerLimit - providerLeasedProbeCalls)`, then `targetRequestLiveCalls = normalRequestCapacity <= 0 ? 0 : max(1, min(normalRequestCapacity, ceil(normalRequestCapacity * 0.95)))` for increase/hold/saturation decisions. New hard request admission still requires an atomic provider request lease acquire with a current `providerLimitVersion` and total request leases plus probe leases below `providerLimit`.
- [ ] If `readyCount > 0`, `providerLeasedLiveRequests < targetRequestLiveCalls`, provider-wide request lease capacity remains, and local routeable capacity remains, increase prompt and request-work backlog targets until provider-wide live calls rise or a bottleneck is identified.
- [ ] If `providerLeasedLiveRequests >= targetRequestLiveCalls` or provider request lease acquire fails because the provider-wide cap is reached, hold the backlog targets and continue replenishing prompt and request-work backlog up to those targets. Reduce only when `localPromptBacklog` or `localRequestWorkBacklog` is above its target and either provider-wide request leases plus probe leases have stayed at or above `providerLimit` for the drain-rate window or completion persistence is backed up.
- [ ] If request or probe lease acquire returns `staleProviderLimitSnapshot`, refresh the owner provider bucket snapshot and `providerLimitVersion`, wake affected waiters after refresh, and do not classify the provider as saturated or admit under the stale snapshot.
- [ ] If no routeable endpoint availability key remains healthy/eligible for this worker because all candidates are in `cooldown`, `misconfigured`, or `probing` with no eligible slot, classify `endpointUnavailable`, avoid increasing backlog targets, and do not attempt normal request lease acquisition on this worker.
- [ ] When endpoint recovery is required for a provider and no routeable endpoint remains on the current worker, this worker must request an eligible endpoint probe lease instead of a normal request lease, subject to probe cooldown/backoff and one live probe per endpoint availability key per worker. If provider capacity is fully occupied by long-running normal requests, probe waiters must subscribe to provider lease release and probe cooldown timers, then retry probe admission when either changes; probe waiters are cancellable on worker shutdown, owner demotion, provider/job closeout, and endpoint recovery. The provider admission service enforces only provider physical-call capacity and holder/lease validity; it must not reject normal lease acquires based on best-effort endpoint telemetry. Existing normal request leases finish naturally; probes do not preempt live requests.
- [ ] If `preparing` age grows while provider-wide request leases are below `targetRequestLiveCalls` and local routeable capacity remains, classify `promptPreparation`.
- [ ] If `waitingForRequestSlot` grows while provider-wide request leases are at or above `targetRequestLiveCalls` but total request plus probe leases remain below `providerLimit`, classify `providerAtTarget`; classify `providerSaturated` only when total request plus probe leases are at or above `providerLimit` or request lease acquire fails at the provider-wide cap.
- [ ] If `waitingForRequestSlot` grows while provider-wide request leases are below `targetRequestLiveCalls`, at least one endpoint availability key is healthy/eligible, shared lease capacity remains, and local worker/fallback slots are available, classify `requestSlotWait`.
- [ ] If `waitingForRequestSlot` grows while provider-wide request leases are below `targetRequestLiveCalls` and worker URLs are locally saturated, classify `workerCapacitySaturated` rather than increasing provider backlog without bound.
- [ ] If `waitingForRequestSlot` grows while provider-wide request leases are below `targetRequestLiveCalls` and shared fallback capacity is saturated, classify `fallbackCapacitySaturated` rather than increasing provider backlog without bound.
- [ ] If `persisting` or `persistingCompletion` age grows, classify `completionPersistence` and avoid claiming more backlog, even when another request attempt for the same prompt is live or waiting.
- [ ] If observed telemetry reports more live requests than provider-wide shared leases or more physical calls than `providerLimit`, show stale-telemetry, missing-lease, or lease-reconciliation diagnostics and do not admit above `providerLimit`. If `observedGlobalProviderLiveRequests` exceeds `observedGlobalEffectiveProviderLimit`, show it as a routeability/diagnostic mismatch, not as permission to exceed the provider-wide cap.
- [ ] If local request telemetry is available but remote telemetry is partial or unavailable, show local scheduling decisions normally and mark aggregate diagnostics as partial.
- [ ] Never change model, provider, thinking level, runtime model, or saved provider limit as part of scheduling.

## Success Criteria

- [ ] With ready work, positive `providerLimit`, available routeable capacity, and provider acceptance, provider-wide request-level `Live LLM calls` across all active judge workers reaches at least `targetRequestLiveCalls` within the configured scheduler/drain-rate window.
- [ ] Aggregate normal request leases plus endpoint probe leases for a provider stay at or below `providerLimit`; stale telemetry or missing-lease mismatches are visible in diagnostics and trigger reconciliation rather than extra admission.
- [ ] Local live request counters on each worker match that worker's held provider request leases after reconciliation, and provider-wide request leases remain the admission authority.
- [ ] If `Live LLM calls` cannot converge, the UI says which stage is limiting throughput.
- [ ] `Claimed` stays bounded by the adaptive prompt backlog target, and chunked judging stays bounded by the adaptive request-work backlog target.
- [ ] Fast GPUs do not drain to zero between scheduler ticks.
- [ ] Endpoint cooldown and misconfiguration are shown as `endpointUnavailable`; warmup and non-endpoint zero-capacity gates are shown as `effectiveCapacityLimited`; none are presented as scheduler underfeeding.
- [ ] `/api/judgmentsjobs/:id`, judgment job health responses, admin runtime routes, Eden types, and `/admin/jobs/:id` use the canonical telemetry/API field names and distinguish lease-authoritative counts from observed telemetry.
