# System prompt variants

The judge system prompt for scientific articles is selected per project through `app.project.system_prompt_variant`.

## Variants

| Variant        | Source                                                        | Used by                                                                                                                 |
| -------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `legacy`       | `src/agent/judge/judgeSinglePromptSystemPrompt.ts`            | Every project that existed before the column, and manual ones created before `screening_v3`.                            |
| `screening_v1` | `src/agent/judge/judgeSinglePromptSystemPromptScreeningV1.ts` | Covidence projects created after the column was added and before 2026-10-19.                                            |
| `screening_v2` | `src/agent/judge/judgeSinglePromptSystemPromptScreeningV2.ts` | Covidence projects created on 2026-10-19 before `screening_v3`; v1 plus the model may quote article_metadata.           |
| `screening_v3` | `src/agent/judge/judgeSinglePromptSystemPromptScreeningV3.ts` | New projects created after `screening_v3` and before `screening_v4` (Covidence and manual); may quote article_metadata. |
| `screening_v4` | `src/agent/judge/judgeSinglePromptSystemPromptScreeningV4.ts` | Every new project since `screening_v4` (Covidence and manual, see "New projects"); may quote article_metadata.          |

`NULL` in the column means `legacy`, and stays that way: existing projects are never backfilled onto a newer variant. The list of variants and the defaults (`defaultSystemPromptVariant` for `NULL`, `newProjectSystemPromptVariant` for new projects) live in `src/agent/judge/systemPromptVariant.ts`. Selection happens in `getSinglePromptSystemPromptForArticle` (`src/agent/judge/judgePromptSelection.ts`). FHIR patient records and structured file imports keep their own system prompts whatever the variant. The chunked evidence system prompt does not vary.

`screening_v1` frames the task as screening a record against one section of the eligibility criteria, applies exclusion lines first, treats any one inclusion line as enough unless the criteria text says otherwise, asks for a structured explanation that ends with `Missing: <fact>` on a `maybe`, restricts quotes to the part of the record the section is about, counts the title as part of the record, and shows yes, no and maybe examples with `'yes' | 'no' | 'maybe'`. The text is the one specified in `forska-plans/2026-09-30-judge-system-prompt-variants.md`; the reasoning behind it is in `CRITERIA_PROMPT_REFINEMENTS_FABLE.md`, section 5.2. `src/agent/judge/judgePromptConstants.test.ts` pins its rules.

`screening_v2` is `screening_v1` with exactly two changes: "You will receive" item 4 no longer says `, do not quote it`, and the quote rule reads `Quotes may come only from article_title, article_summary, article_metadata, or article_fulltext.` `src/agent/judge/judgeSinglePromptSystemPromptScreeningV2.test.ts` pins that it is v1 with exactly those two replacements. Existing projects keep their stored variant; nothing is backfilled. A variant's frozen text is never edited, so a prompt change becomes a new variant.

Metadata quotes are a per-variant capability: `systemPromptVariantAllowsArticleMetadataQuotes` in `src/agent/judge/systemPromptVariant.ts` is true for `screening_v2`, `screening_v3` and `screening_v4`. When a project uses metadata and its variant has the capability, two things change. First, `getSinglePromptJudgmentRequest` puts the metadata lines after the title in `recordText`. They are the same `label: value` lines as the prompt block, and `none available` is left out. Quote validation therefore keeps metadata quotes on single, part and merge calls. Second, the part and merge instructions name the metadata as a quote source. For `legacy` and `screening_v1`, with `use_metadata` on or off, every prompt string and `recordText` stay byte-identical to main. `src/agent/judge/judgePromptVariantParity.test.ts` pins this with hashes.

`screening_v3` replaces the v1 rules behind the false negatives of the 2026-10-19 sensitivity analysis (`forska-plans/2026-10-19-screening-v3-system-prompt.md`): it says the step is a filter whose included records go on to the next step, treats a word only in the title, background, aim or conclusion as a weak signal that counts when the methods or results show it, applies an exclusion line only when the record shows it (a record that also matches an inclusion line on the same point is answered by the inclusion line, or maybe), answers no on a complete record that is silent and maybe on a thin record (empty, a few sentences, cut off, background only, or the start of the main text), and answers maybe only when the criteria text does not say what to assume. Like `screening_v2` it lists `article_metadata` as a quote source and has the metadata-quote capability, so with `use_metadata` on its `recordText`, quote validation and part/merge instructions behave exactly as for `screening_v2`; `judgePromptVariantParity.test.ts` checks that v3 differs from v2 only in the system prompt. It has four `Request:` / `Response:` examples. The default text is the canonical `forska-plans/2026-10-19-screening-v3-prompt.txt` byte for byte (1,552 o200k tokens); the Anthropic text replaces its first sentence with the v1 medical-research framing and adds the v1 harmlessness paragraph, and the rest is identical. `src/agent/judge/judgePromptConstants.test.ts` pins its rules and the SHA-256 of both texts.

`screening_v4` keeps the v3 opening paragraph, evidence rule, exclusion rule, quote rules and explanation format, and changes how a record that lacks a needed fact is answered (`forska-plans/2026-10-21-screening-v4-prompt.txt`). A fact about the study that the record leaves unstated is missing information, not evidence of absence: the model answers maybe and names the missing fact, for a complete abstract that leaves such a fact unstated (a hospital study that names no country, an intervention named but not described) as much as for a thin record. It assumes a missing fact only when the criteria text says what to assume, and answers no for it only when the criteria text says that a missing fact counts as no. No is reserved for a record that shows an exclusion, or whose report of what the study did or found leaves no room for what the section asks for, for example one time point and no comparison, or reported results none of which is a listed outcome. When the output_type has no maybe, those cases are answered yes. The filtering-step paragraph adds that the next step reads the full text, that a wrong exclusion loses the study for good and that a wrong inclusion costs one more look. It has five `Request:` / `Response:` examples; the new third one shows a complete abstract that names only a 900-bed tertiary hospital, answered maybe with `Missing: country`. Its metadata-quote behaviour is that of `screening_v3`, and `judgePromptVariantParity.test.ts` checks that v4 differs from v3 only in the system prompt. The default text is the canonical file byte for byte, final newline included (1,973 o200k tokens); the Anthropic text is built as for v3 (2,066 tokens). `src/agent/judge/judgePromptConstants.test.ts` pins its rules and the SHA-256 of both texts.

## New projects

Every route that creates a project without copying one writes `newProjectSystemPromptVariant` (`screening_v4`) explicitly:

- `POST /api/projects` when the body has no `systemPromptVariant` (pass another variant to choose it).
- Covidence datasource create (`getOrCreateCovidenceProject` in `src/server/services/covidenceImportService.ts`), for the title/abstract and the full-text project.
- `POST /api/subprojects` when the source projects do not share one variant, or when there are no source projects.

Routes that copy a project keep the source's variant: clone copies the stored value (`NULL` stays `NULL`), `POST /api/subprojects` keeps the variant when all source projects share one, and project transfer import stores the package's variant (a package without one imports as `legacy`).

## How the variant reaches the model

- Judgment jobs copy it into the per-job SQLite `job_info` table at initialization (`system_prompt_variant`), so a running job keeps the variant it started with. Older job databases get the column on open and read as `legacy`. The fifth content flag `use_metadata` is frozen the same way (`job_info.use_metadata INTEGER NOT NULL DEFAULT 0`, older job databases read `0`).
- Owner-backed judge workers receive it in `OwnerBackedJudgmentJobInfo` from `GET /api/judgmentsjobs/:id/runtime`. That route reads the job's `job_info` copy and only falls back to the live `app.project` value when the job has no SQLite store yet.
- `PromptToProcess.systemPromptVariant` carries it to `judgeSinglePrompt`.
- The prompt preview (`GET /api/projects/:id/prompts/:promptId/preview`, the "Preview Prompt" button on the Project Details page) uses the project's variant and reports it as `systemPromptVariant`. When no served article is available yet (no ready review-serving snapshot, no articles, or no full text), the response is still `unavailable` for the user prompt, but it carries the current `systemPrompt` built for a plain scientific article with the project's provider, so the page always shows the system prompt in use.

## Article metadata block

With `use_metadata` on, the user prompt has an `## article_metadata` block after the title. `getArticleMetadataLines` in `src/agent/judge/articleMetadataPrompt.ts` builds it as `label: value` lines. The same lines feed `recordText` and quote validation for the variants with the metadata-quote capability, the Article Details pages (`articleMetadata` from `GET /api/articles/:id` and from the project review details) and the `articleMetadataDigest` in a project transfer judgment input signature. A line without a value is left out, and a block without lines reads `none available`. The lines, in order:

| Label                | Value                                                                                                                                                                        |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `journal`            | source metadata `journalTitle`                                                                                                                                               |
| `year`               | `publicationYear`, else the year of `article_created_at`                                                                                                                     |
| `volume/issue/pages` | volume, issue and pages as `12(3):100-110`                                                                                                                                   |
| `publication_type`   | `publicationType`, else `publication_status`, else `preprint` for a preprint                                                                                                 |
| `doi`                | `article.doi`                                                                                                                                                                |
| `pmid`               | `article.pubmed_id`                                                                                                                                                          |
| `registry_id`        | the first trial-registry id (`getTrialRegistryIdentifier` in `src/utils/trialRegistryIdentifier.ts`) found in `accessionNumber`, then in `sourceUrl`, then in `journalTitle` |
| `accession`          | `accessionNumber` when it holds no registry id, for example `WOS:…`, an Embase number or a CENTRAL `CN-…`                                                                    |
| `source_url`         | from `sourceUrl`: the first trial-registry url (`isTrialRegistryUrl`), else the first url when the article has no DOI                                                        |

Covidence exports a trial-registry record (ClinicalTrials.gov, CTRI, IRCT, ChiCTR, ISRCTN, ANZCTR, ReBEC, TCTR, PACTR and others) with an empty Journal. Its identity is in Accession Number (`NCT…`, ClinicalTrials.gov only) and in the DOI column, which then holds the registry url, for example `https://clinicaltrials.gov/study/NCT…` or `http://www.ctri.nic.in/Clinicaltrials/pmaindet2.php?trialid=3379`. The Covidence import stores that url as `sourceUrl` in the article source metadata and the import metadata. It takes the DOI column when it is an http(s) url that is not a doi.org url, else the URL column (RIS `UR`, `L1`–`L4`) under the same rule (`getArticleSourceUrl` in `src/utils/articleSourceUrl.ts`). Embase joins two urls into one value (`…&from=exporthttps://clinicaltrials.gov/study/NCT…`). The value is stored as it is and split when the line is built. Records imported before the field existed get it from migration `0274_covidenceSourceUrlBackfill.sql`. Like `0257`, it fills a missing `sourceUrl` from the raw Covidence citation on the source records, the current import links and the article. The article takes the value from its earliest Covidence source record.

The metadata text is not part of the judgment identity (see "Judgment identity"), so these lines needed no identity migration, and existing judgments stay visible. The block is the same for every variant. With `use_metadata` on, a record that has an accession number or a source url now gets a longer block under `legacy` and `screening_v1` too. Records with neither are unchanged. Judgments already stored were made with the shorter block. Re-judging such a record, or judging it in a new project, sends the new lines.

## Switching a project

There is no UI switch. Use the API:

```http
PATCH /api/projects/:id/edit
{"systemPromptVariant": "screening_v1"}
```

`POST /api/projects` accepts the same optional field and uses `screening_v4` without it. The variant is protected like the content settings: once a judgment job exists for the project the edit route answers 409, so a project's judgments all come from one system prompt. Existing projects therefore keep `legacy` unless they are switched before their first job. Clone copies the source project's variant. Project transfer exports the variant in the project settings when it is not `legacy`, import validates and stores it, and the judgment input signature (`systemPromptFamily: getSinglePromptSystemPromptForArticle:v2`) digests the system prompt of the exporting project's variant and names it in `request.systemPromptVariant`.

## Judgment identity

The variant is part of the judgment identity: `(article, prompt, model, use_title, use_abstract, use_fulltext, use_fulltext_no_images, use_metadata, system_prompt_variant)`. `app.judgment.system_prompt_variant` is `VARCHAR NOT NULL DEFAULT 'legacy'` and is included in the table's UNIQUE constraint and in `idx_app_judgment_lookup`. Migration `0255_judgmentUseMetadata.sql` rebuilt both again to add the content flag `use_metadata BOOLEAN NOT NULL DEFAULT FALSE` (existing judgments `FALSE`); a project matches it with `COALESCE(project.use_metadata, FALSE)`. A project only sees and reuses judgments whose variant equals its own `COALESCE(system_prompt_variant, 'legacy')` (`getProjectVisibleJudgmentNaturalKeySql` in `src/server/services/projectVisibleJudgmentRule.ts`). Two projects with the same model, content settings and prompt text but different variants therefore judge separately.

Since migration `0267_judgmentFullTextStrategy.sql` the full UNIQUE on `app.judgment` is `(article_id, prompt_id, model_id, use_title, use_abstract, use_fulltext, use_fulltext_no_images, use_metadata, system_prompt_variant, full_text_strategy_id, delete_generation)`.

`use_fulltext_no_images` is a frozen legacy identity dimension, like `delete_generation`. Full text is chosen with `use_fulltext` plus a full-text strategy (figure mode `none` replaces "no images"), so nothing writes `TRUE` into new rows. The column stays in the UNIQUE because other installations can hold legacy judgments that differ only in this flag; dropping it from the key would turn them into duplicates. The rules:

- No API input accepts it. Project create, `PATCH /api/projects/:id`, `PATCH /api/projects/:id/edit`, clone, `POST /api/subprojects` and the comparison-project create, create-from-project and edit bodies answer 400 when the field is present, whatever its value (`rejectLegacyFullTextNoImagesBody`). Elysia drops unknown body keys without an error, so the check runs as a `transform` hook before validation. The judge-worker completion body (`POST /api/judgmentsjobs/:id/completions`) still carries the flag, because it is part of the claim identity.
- A project or comparison that already has it set keeps it. Its legacy judgments (`fts-legacy-v0`) stay visible through it. Clone, create-subproject and comparison create-from-project copy the stored value. Comparison edit keeps the stored value.
- An edit that gives a legacy no-images project a full-text strategy (only possible before its first job) clears the flag together with the strategy change. The project then stops seeing its legacy judgments, as any strategy change does.
- Identity code keeps reading and writing the column: the judgment store, outbox import, project transfer, review-change deltas, execution snapshots, comparison content variants and keys, and judgment-context derivation. Behaviour code does not branch on it. Whether a project uses full text comes from `use_fulltext` or a stored `fts-legacy-v0` strategy.
- UI shows legacy rows as "full text (legacy, no images)" and has no control for the flag.

Migration `0251_judgmentSystemPromptVariant.sql` rebuilds `app.judgment` together with `app.judgment_assessment`. DuckDB cannot alter a UNIQUE constraint, and `judgment_assessment` has a foreign key to `app.judgment`. The migration copies every existing judgment as `legacy`, because every judgment stored before it was produced with the legacy prompt. On a full clone of the live database (1.04M judgments) the rebuild took about 23 s.

How the variant gets onto a stored judgment:

- `recordJudgmentSuccess` writes it into the per-job SQLite `judgment_outbox.system_prompt_variant` from the job's frozen `job_info` value. The optional `systemPromptVariant` in the completion payload (`JudgeWorkerCompletionPayload`, `POST /api/judgmentsjobs/:id/completions`) is used only when the job has no `job_info` row. Older job databases get the outbox column on open, and their rows without a value take the job's `job_info` variant when imported. `judgment_outbox.use_metadata` is stamped from `job_info` the same way; the optional `useMetadata` in the completion payload is also part of the claim identity, so a completion whose flag contradicts the job is rejected with `snapshot claim identity mismatch for useMetadata`, and a payload without it (journal entries written before the flag existed) is treated as `false`.
- The outbox import (`judgmentsJobsMarkDirtyWork.ts`) inserts the variant into `app.judgment` and uses it in the `ON CONFLICT` target.
- The already-judged checks in `processPromptWithLLM` and `storeSinglePromptJudgment` include the variant, so a `screening_v1` job does not skip an article because a `legacy` judgment exists.
